## Ссылки upstream skills на соседей

Skills из `obra/superpowers` ссылаются на соседей как `superpowers:<name>`, skills Мэтта — как `tdd` и `code-review`. Соседа с таким именем проект может держать сам; тогда ссылка ведёт к нему. Если его нет:

- `superpowers:test-driven-development` и `tdd` — это `test-driven-development`;
- `superpowers:verification-before-completion` — `verify-change`;
- `code-review` — `review-changes` в субагенте с чистым контекстом, если инструмент умеет: передай ему scope, ticket и spec, свежий `verify-change` report. Режим — по [Authority](../engineering/delivery.md#authority).

## `implement-spec` в этом репозитории

Upstream собирает инициативу параллельными исполнителями. У нас так же, с дополнениями:

- **Исполнитель** — субагент с `implement` вместо голого `tdd`: внутри TDD, `review-changes`, статусы и коммит ticket.
- **Параллельно — только независимые.** Одновременно идут tickets с frontier, которые не блокируют друг друга и не правят одни и те же файлы; остальные ждут слияния своих `Blocked by`. Зависимость по общему файлу, которой нет в `Blocked by`, — повод не запускать пару параллельно.
- **Worktree исполнителя** — свой worktree и ветка на ticket; `pnpm env:copy` до работы. Dev-сервер, порт и browser session у каждого worktree свои (`pnpm -s browser:port`); `pnpm dev` останавливается до отчёта.
- **Общие данные dev-контура.** Исполнители, которые меняют данные в одном dev-контуре, работают с разными тестовыми сущностями: имя сущности содержит ключ ticket.
- **Интеграционная ветка.** Запуск `/implement-spec` — просьба создать её от текущей ветки. Draft MR/PR и push — только по отдельной просьбе ([delivery.md](../engineering/delivery.md#authority)).
- **Стоп.** Исполнитель вернул `NOT READY` или упёрся в продуктовое решение — оркестратор останавливается и спрашивает пользователя, следующий ticket не берёт.
- **Финал.** `review-changes` по всей ветке против базы в субагенте; инициатива `done` — решение человека по [статусам](issue-tracker.md#статусы).

## `correct` в этом репозитории

Upstream `correct` не знает, где лежат наши сессии и как мы оформляем исключения. Дополнения:

- **Источники.** Сессии Claude Code — `~/.claude/projects/*{{PROJECT}}*`, Cursor — `~/.cursor/projects/*{{PROJECT}}*`, Codex — `~/.codex/sessions/`. Служебные сессии Codex, которые начинаются с «The following is the Codex agent history», пропускай; копии одного треда считай один раз. Плюс `git log` и комментарии к MR/PR, если к хостингу есть доступ.
- **Окно.** По умолчанию — с прошлого запуска, иначе две недели; окно назови в отчёте.
- **Числа задач.** Посчитай за окно строку «Задачи» по определениям из [очереди повторов](repeats-queue.md#как-дописывать): задачи из сессий, дефекты после `READY` — по `git log` (fix-коммиты в тех же файлах) и комментариям к MR/PR. Число, которое нельзя установить, пиши `?` с причиной, а не оценкой.
- **Где поправки.** Пользователь часто отвечает в блоках `<!-- reply -->` и цитатах ответа агента, а не только обычным текстом.
- **Уже исправлено?** Каждый класс сверь с `git log` и текущими правилами: исправленное после случаев в таблицу не идёт, а перечисляется отдельно.
- **Пути в конфигах проверок** (списки файлов в lint-правилах, baseline) после переездов файлов тоже класс: правило, которое смотрит на несуществующий путь, молча перестаёт работать.
- **Сначала таблица.** Перед правками покажи классы: число случаев с примерами, уровень, правка, оценка в днях и с чего начать. Правь после выбора пользователя.
- **Исключения** — baseline-список, который пересобирает скрипт, как `pnpm lint:size:update`; срок и владелец — в заметке `docs/ideas/`.
- **Таблица «правило → чем проверяется»** — пометки «Проверяет lint» в документе правила, например в styleguide. В `AGENTS.md` только guardrails.
- **Правка текстом.** Класс, который закрывается правилом или skill, пиши по `writing-for-agents`.
- **Классы общения и процесса** (непонятный ответ, вопрос не задан) выше правила обычно не поднимаются: правило в `AGENTS.md` или skill, а проверка — формат ответа в skill.
- **Потери времени без поправки** — долгий поиск файла, тяжёлые вызовы, нехватка доступа или логов — перечисли отдельно с предложением.
- **CI.** Новая проверка входит в `pnpm check`: CI запускает `pnpm verify`, а он включает `pnpm check`.

## `maintain-verification-skill` в этом репозитории

Upstream skill написан под Cursor, а переходник `docs/harness/claude-code.md`, на который он ссылается, мы не подключали. Соответствия:

- **Что сопровождаем** — [карту фич](../../.agents/skills/verify-change/features/README.md) в `verify-change`. Launch, Doctor и cleanup — по [browser-testing.md](../engineering/browser-testing.md): `pnpm dev`, `pnpm browser:login`, `pnpm browser:doctor`.
- **Вместо PR** — локальный коммит правок карты через `commit-changes`; push и MR/PR — по просьбе.
- **Субагенты-читатели** — встроенные субагенты инструмента; нет их — читай фичи по очереди сам.
- **Mutation** — только в разрешённом dev-контуре с понятной очисткой; отправку форм без разрешения не проходи, а помечай непроверенной.
- **Когда** — раз в две недели или после заметной правки UI фичи из карты.
