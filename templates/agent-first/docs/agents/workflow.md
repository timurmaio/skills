# Agent workflow

## Единый цикл

1. Сформулировать цель и границы изменения.
2. Выполнить реализацию или диагностику подходящим skill.
3. Собрать свежий evidence через `verify-change` или применимую project-команду.
4. Запустить `review-changes`: он исправит найденное в своём diff. Только посмотреть — попросить ревью без правок.
5. Закоммитить свой slice через `commit-changes` и подготовить MR/PR handoff.

Skills не создают независимые процессы: они стандартизируют отдельные этапы этого workflow.
Ранний статический review можно выполнить до `READY`, чтобы найти дефекты, но он обязан отметить отсутствующий evidence и не заменяет финальную последовательность verification → review.

## Подключение skills

Источник skills — `.agents/skills/`. Codex и Cursor читают его сами. Claude Code видит skills через закоммиченные симлинки `.claude/skills/<name>` → `../../.agents/skills/<name>`. Из остального в `.claude/` закоммичен только `settings.json` с общими разрешениями, личные — в `.claude/settings.local.json`; прочее gitignored.

Добавляя или переименовывая skill, обновите симлинки в том же diff: `bash scripts/linkClaudeSkills.sh` создаёт недостающие и удаляет висячие, `pnpm lint:skills` падает, если симлинки разошлись с `.agents/skills/`.

Vendored skills ставит CLI [`skills`](https://github.com/vercel-labs/skills) и записывает хеш папки в `skills-lock.json`. Обновление одного skill из upstream:

```bash
npx -y skills add <source> --skill <name> -a codex --copy -y
```

## Worktree и локальный env

Создавая git worktree или начиная в нём работу, агент копирует локальный env из основного checkout. Это обычная копия, не symlink: у разных worktree окружение может различаться, и правка файла в одном checkout не меняет остальные.

Из каталога worktree:

```bash
pnpm env:copy
```

Команда копирует `.env.local` и, если он есть, `.env.browser.local` для [browser verification](../engineering/browser-testing.md). Основной checkout — первая запись `git worktree list --porcelain`. Файл, который в worktree уже есть, не перезаписывается — так в worktree можно держать своё окружение.

Env-файлы остаются gitignored и не коммитятся. Credentials, tokens и значения env нельзя копировать в документы или tool output. Существующая копия не подхватывает поздние правки файла в основном checkout.

## Как формулировать запрос

- Можно описать цель обычным языком: «проверь diff», «разбери падение CI», «создай домен».
- Если нужен предсказуемый workflow, назовите skill явно.
- Что агент коммитит сам, а что запрашивается явно — [delivery workflow](../engineering/delivery.md#authority).
- Релизы, публикации пакетов и другие внешние действия — только явным именем project skill с `disable-model-invocation: true`: агент не стартует их сам.

## Выбор skill

Человек запускает только точки входа из флоу, ситуативные и рутину; остальные вызываются внутри связок. Skills со слешем (`disable-model-invocation`) запускаются только командой пользователя. Полный список определяется содержимым `.agents/skills/`, пошаговые инструкции — в их `SKILL.md`.

### Флоу разработчика

Путь выбирается по размеру задачи.

| Задача                         | Путь                                                                                                                              |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| Маленькая и понятная задача    | Описать цель и критерий готовности → агент реализует, проверяет, ревьюит и коммитит                                               |
| Баг, упавший тест, lint или CI | `systematic-debugging` → фикс с регрессионным тестом. CI — по шагам [CI failure loop](../engineering/delivery.md#ci-failure-loop) |
| Фича среднего размера          | `grilling` → `/to-spec` → `/to-tickets` → `/implement` на каждый ticket или `/implement-spec` на все                              |
| Инициатива больше одной сессии | `/wayfinder` → решения по его tickets → `/to-spec` → `/to-tickets` → `/implement-spec`                                            |
| Сдача                          | `summarize-changes` — описание MR/PR; замечания ревью и комментарии к MR/PR — `receiving-code-review`                             |

### Связки: что вызывается само

| Что запущено                           | Сам вызывает                                                                                                                                                                                           |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Любая правка кода                      | `test-driven-development` по [testing.md](../engineering/testing.md), `verify-change`, `review-changes` и `commit-changes` по правилам «Готово» и «Коммиты» в `AGENTS.md`                              |
| `implement`                            | `test-driven-development`, `review-changes` в субагенте; по `AGENTS.md` и [issue-tracker](issue-tracker.md#когда-skill-говорит-возьми-ticket) — `verify-change`, `summarize-changes`, `commit-changes` |
| `implement-spec`                       | `implement` в субагенте на каждый ticket, в конце `review-changes` по всей ветке                                                                                                                       |
| `review-changes`                       | `verify-change` после своих правок                                                                                                                                                                     |
| `systematic-debugging`                 | `test-driven-development` для регрессионного теста, `verify-change`                                                                                                                                    |
| `wayfinder`                            | `research`, `prototype`, `grilling`, `domain-modeling` — по типу ticket                                                                                                                                |
| `correct`, правка skills и `AGENTS.md` | `writing-for-agents` — как писать текст для агента                                                                                                                                                     |

Руками `test-driven-development`, `verify-change`, `research`, `prototype`, `domain-modeling` и `writing-for-agents` не вызывай — разве что как отдельный вопрос: «готово ли это?», «проверь факт», «собери макет», «уточни термин».

### Ситуативные

| Задача                                           | Skill            |
| ------------------------------------------------ | ---------------- |
| Понять, что изменилось и какие решения ждут тебя | `catch-up`       |
| Записать идею или техдолг на потом               | `capture-idea`   |
| Закоммитить вне `implement`                      | `commit-changes` |

`review-changes` можно запустить и напрямую: он исправляет найденное в своём diff и read-only по просьбе или для чужого кода.

### Рутина

| Когда                                                       | Кто                | Что                                                                              |
| ----------------------------------------------------------- | ------------------ | -------------------------------------------------------------------------------- |
| Раз в неделю                                                | Каждый разработчик | `/correct`: «разбери мои сессии за неделю, без правок, запиши в очередь»         |
| Раз в неделю                                                | Владелец сетапа    | Разбирает [очередь повторов](repeats-queue.md) и запускает `/correct` с правками |
| Сразу после сессии, которая пошла не так                    | Тот, кто работал   | `/correct` по этой сессии                                                        |
| Раз в две недели или после заметной правки UI фичи из карты | Владелец сетапа    | `/maintain-verification-skill` — сверить карту фич с кодом и приложением         |

### Разбор сессий: как устроен

Агент повторяет ошибки по-разному у каждого, поэтому сессии разбирает каждый разработчик на своей машине — `correct` найдёт их в домашней папке.

1. **Каждый, раз в неделю:** запусти `/correct` в режиме очереди — «разбери мои сессии за неделю, без правок, запиши в очередь». Агент дописывает таблицу классов в [repeats-queue.md](repeats-queue.md) и коммитит её отдельным коммитом документации.
2. **Владелец сетапа, раз в неделю:** читает очередь целиком, выбирает классы, которые повторяются у нескольких людей или дорого стоят, и запускает `/correct` уже с правками по ним. Закрытый класс помечается коммитом.

Очередь, а не мгновенная правка: общая причина видна только по нескольким сессиям и людям.

**Сессия пошла не так** — агент долго искал, сделал не то или нарушил правило — не жди недели: запусти `/correct` по этой сессии, пока она свежая. Без правок находки идут в ту же очередь. Правка сразу — только если класс уже есть в очереди или его поправил пользователь.

Автоматически, без человека, `correct` не запускаем: агент сам будет находить ложные проблемы и уводить сетап не туда.

## Поддержка инструкций

- [AGENTS.md](../../AGENTS.md) держит только hard guardrails и pointers; [CODING_STANDARDS.md](../../CODING_STANDARDS.md) — правила для каждого изменения кода и карту инженерных документов. Каждое правило храните в одном месте — в ближайшем тематическом документе или skill; из остальных мест ставьте pointer с условием, когда его открывать.
- `description` project-owned skills пишите на английском: каталог смешан с vendored upstream skills, которые не переводятся. Триггерные фразы пользователя можно цитировать по-русски. Тело skill — на русском.
- Повторяющееся замечание закрепляйте механически: lint rule, тестом, validator или инструкцией skill.
- Решения из чата, ревью и QA, важные для будущих задач, переносите в репозиторий.
- Переименовали или удалили документ или раздел — обновите ссылки в том же diff; проверяет `pnpm lint:links`.
- Изменили skill — проверьте его вслепую: два субагента выполняют одну и ту же задачу со старой и новой версией (или с upstream), третий сравнивает результаты, не зная, где какая. Skill, которым пользуются Codex и Cursor, прогоните и на их моделях. Шаг, который модель пропускает, уточните или замените скриптом: скрипт работает одинаково на любой модели.
