# Архитектура доменов

[Карта инженерной документации](../../CODING_STANDARDS.md).

Бизнес-домены живут в `src/features/<domain-name>/`. Каждый домен изолирован: компоненты, хуки, типы, переводы и документация.

## Именование

| Сущность                    | Формат                          | Пример для `pixel-events`        |
| --------------------------- | ------------------------------- | -------------------------------- |
| Папка                       | `kebab-case`, `[a-z][a-z0-9-]*` | `pixel-events`                   |
| Namespace переводов         | PascalCase                      | `PixelEvents`                    |
| Категория событий аналитики | `snake_case` от имени папки     | `pixel_events`                   |
| Импорт снаружи              | только корень домена            | `@/features/pixel-events`        |

Namespace переводов **может не совпадать** с именем папки (например папка `invoices`, ключ `Invoice`). Для нового домена выберите его заранее и используйте везде одинаково.

## Структура папки

### Минимальный домен

```
src/features/<domain>/
├── components/       # React-компоненты
├── hooks/            # data hooks и query keys
├── messages/         # переводы домена, если в проекте есть i18n
├── types.ts
├── utils.ts          # или helpers/ для нескольких файлов
├── constants.ts      # при необходимости
└── index.ts          # публичный API домена
```

### Опционально

- `docs/` внутри домена — `GLOSSARY.md`, спецификации, runbook, `adr/`. Правила — [docs/agents/domain.md](../agents/domain.md).
- Страницы фреймворка (`src/app/...`, `src/pages/...`) — не внутри `features/`: маршрут импортирует домен через публичный API.

## Раскладка внутри домена

По пути файла видно его роль: поле, блок, страница, запрос, состояние экрана, маппер, правило. Новый файл кладётся по роли и владельцу, а не рядом с похожим именем.

### Уровни

```
src/features/<domain>/
  <срез>/            только если в домене несколько независимых частей
    <модуль>/        крупная UI-сущность со своим входом
      <роль>/        файлы одной роли
```

- **Срез** — независимая часть домена со своей границей зависимостей: например, общая форма `form/`, версии `v1/` и `v2/`, общий код `shared/`. Маленький домен срезов не заводит и сразу делится на ролевые папки.
- **Модуль** — крупная UI-сущность с входом `index.ts(x)`: превью, массовое действие, шаги формы. Снаружи модуля импортируют только вход. Подпапки `model/`, `ui/`, `hooks/` появляются, когда файлов больше ~8; до этого модуль плоский.
- **Ролевая папка** — файлы одной роли.

### Роли

| Папка                | Что внутри                                                                                                                                       |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `fields/`            | поля формы и их контролы, по доменным подпапкам; селект живёт рядом со своим полем                                                               |
| `blocks/`            | блоки из нескольких полей                                                                                                                        |
| `ui/`                | визуальные части без привязки к форме, которыми пользуются несколько модулей одного владельца                                                    |
| `model/`             | чистые правила, типы, константы, политики; без React-хуков и без UI-папок своего владельца                                                       |
| `hooks/`             | хуки состояния и оркестрации; `hooks/queries/` — серверные запросы и их ключи                                                                    |
| `api/`               | общение с backend: `requests/` (вызовы), `queries/` (кэш серверного состояния), `mappers/` (запрос и ответ), `outcomes/` (разбор исходов и ошибок) |
| `testing/`           | тестовая поддержка: стенды, фикстуры; продакшн-код её не импортирует                                                                             |
| `docs/`, `messages/` | документация и переводы домена                                                                                                                   |

Страница (`View*`) — папка компонента (`components/ViewList/`) или файл в папке своей страницы, где рядом лежат её хуки и части.

### Владелец файла

Файл лежит у ближайшего общего родителя всех своих потребителей. Один потребитель — рядом с ним. Потребители в двух модулях — в ролевой папке их общего владельца (`form/ui/`). Чистое правило, которым пользуются и поле, и модель, живёт в модели: зависимости идут от UI к модели, а не обратно.

### Имена

- **Папка-хранилище** (ролевая папка, модуль, срез) — строчными, из нескольких слов через дефис: `fields/`, `bulk-copy/`. camelCase для папок не используется.
- **Папка одного компонента** — PascalCase с `index.tsx`: `ViewCreate/`, `Table/`. Вспомогательные файлы этого компонента лежат в ней же.
- **Файлы:** компонент — `PascalCase.tsx`, хук — `useX.ts`, остальное — `camelCase.ts`.
- **Исключения:** сгенерированные файлы и служебные файлы фреймворка (`not-found.tsx`, `page.tsx`).

### Импорты

Алиас `@/features/<domain>/...` внутри домена можно всегда. Относительный путь — только внутри своей папки (`./`, вглубь; тест из `__tests__/` смотрит в свою папку через `../`); за пределы папки относительный путь не выходит: папка переезжает, не переписывая импорты соседей. Снаружи домена — только публичный API (`@/features/<domain>`).

### Проверка раскладки

Границы срезов и направление зависимостей домен может закрепить тестом по импортам или lint-правилом. Для остальных доменов правило — этот текст.

## Публичный API (`index.ts`)

Экспортировать только то, что нужно снаружи домена: типы, хуки, ключевые компоненты, утилиты, константы. Экспорты перечисляются явно, без `export *` — подробно в skill `feature-modules` ([timurmaio/skills](https://github.com/timurmaio/skills)).

Импорт внутренностей чужого домена должен ронять lint (`no-restricted-imports` с шаблоном `@/features/*/**` или своё правило). Существующие нарушения при внедрении правила — baseline-список, который пересобирает скрипт и который только сужается; вручную в него не добавляют.

## Принципы

1. **Изоляция** — не тянуть внутренности чужого домена; только публичный API.
2. **Нет cross-domain импортов** «вглубь» — только через `index.ts` или общие слои (дизайн-система, `@/lib`).
3. **Согласованность имён** — один namespace переводов и одна категория аналитики на весь домен.

## Границы данных

- **Типизированный backend API:** По умолчанию доверяем согласованному контракту API проекта (типы из OpenAPI или аналогичной схемы). Не добавляйте без согласованной причины локальные runtime-парсеры, повторяющие структуру типизированного ответа (`isRecord`, проверки каждого свойства, рекурсивный parser). TypeScript не проверяет ответ во время выполнения — это проектный компромисс, а не гарантия runtime-валидации. Риск конкретной интеграции может оправдывать дополнительную проверку: согласуйте источник данных, причину и поведение при нарушении контракта, затем проверяйте ответ на выбранной границе API, а не в каждом control.
- **Нетипизированные и недоверенные источники:** Пользовательский ввод, search params, storage и действительно неизвестные внешние данные проверяйте на входе схемой или явным parser. Передавайте дальше проверенную структуру; не восстанавливайте её форму в глубине UI. Отсутствующий тип API уточняйте в контракте или адаптере; произвольное `as` не превращает неизвестные данные в доверенный ответ.
- **Нормализация и бизнес-валидация:** Маппинг API-модели в доменную, преобразование форматов и проверка бизнес-ограничений остаются необходимыми по сценарию. Политика доверия не отменяет обработку ошибок запроса и клиентскую валидацию формы по [forms.md](forms.md).

## Владение переиспользуемым кодом

- Helpers, formatters, business rules и controls с доменной семантикой принадлежат соответствующему домену независимо от количества потребителей. Например, форматирование денег и валюты живёт в `currency`, а не в глобальном `src/utils`; другие домены используют его публичный API.
- `src/utils` предназначен для действительно общих функций без доменных знаний. Сам по себе вызов из двух features не повод переносить helper в глобальный слой.
- Общий бизнес-UI остаётся в каталоге домена, а дизайн-система содержит компоненты без доменной семантики. При совпадающем поведении различия transport/API изолируйте в адаптерах, выбираемых composition-слоем, а не в копиях UI. Для форм подробный контракт описан в [forms.md](forms.md#общий-каталог-контролов-и-разные-api).

### Изоляция vs публичный API (хуки)

**Суть:** сосед импортирует **контракт** домена (`index.ts`), а не **реализацию** (store, query keys, пути в `hooks/`). Экспорт хука — часть контракта, это не нарушение изоляции.

| Можно снаружи                              | Нельзя снаружи                                 |
| ------------------------------------------ | ---------------------------------------------- |
| `useCurrency()`, `useProjectsShortList()`  | `useCurrencyStore`, `projectQueryKeys`         |
| `type ProjectFullInfo`                     | `@/features/projects/hooks/...` (deep import)  |

**Где живёт data-hook:** в домене-владельце данных; `src/api` — только client и схемы, без доменной семантики. Сброс чужого кэша — через публичную `invalidateX()`, не через экспорт query keys.

**Один хук или свой в каждом домене?**

- Данные сущности → хук в её домене, соседи импортируют из его публичного API.
- Не дублировать тот же fetch в нескольких доменах.
- Локальный хук — только обёртка под UI своей страницы (внутри вызывает публичный API соседа).

**Терминология (для ревью):** публичный API обеспечивает инкапсуляцию; импорт через `index.ts` сам по себе не означает Dependency Inversion (DIP) или Dependency Injection (DI). DI — передача зависимости потребителю извне, DIP — зависимость от абстракций вместо деталей реализации. Папка feature также не становится автоматически Bounded Context: для этого нужна отдельная согласованная доменная модель.

## Интеграции домена

Опишите здесь шаги, которые проект требует для каждого домена, — то, что агент иначе забудет. Типичные пункты:

- **Переводы:** где регистрируются messages домена, формат ключей, какие локали обязательны.
- **Аналитика:** события — по [analytics.md](analytics.md), только через публичную границу аналитики проекта.
- **Маршруты:** где лежат страницы и как они подключают домен.

## Создание домена

Перед созданием уточните имя папки, namespace переводов, эталонный домен, нужны ли аналитика и маршруты. Копируйте структуру эталона, не его логику. `helpers.ts`, `ViewList` и аналитику — только по задаче.

## Проверка после создания или правок

`pnpm check` проверяет границы доменов и типы. Руками сверьте то, что он не видит: шаги из [«Интеграций домена»](#интеграции-домена) выполнены, имена из [таблицы](#именование) совпадают во всех местах.
