## Компоненты (React)

- **Типизация Props:** Собственный объектный контракт `props` описывайте через `interface`. Интерфейс пропсов всегда должен называться `Props`, за исключением случаев, когда пропсы экспортируются (тогда используется `ComponentNameProps`). Производные контракты, unions и mapped/conditional types описывайте через `type` согласно [общему правилу TypeScript](code.md#typescript).
- **Деструктуризация пропсов:** Пропсы всегда передаются как единый объект `props: Props`, а деструктуризация выполняется внутри функции. Lint: собственное правило проекта (запрет деструктуризации в параметрах компонента).
- **Изображения:** Используйте одну абстракцию изображений проекта (обычный `img`, компонент дизайн-системы или компонент фреймворка) — какую, решите один раз и запишите сюда.

  ```tsx
  // ПЛОХО: деструктуризация в параметрах
  interface ActionDisplayProps {
  	label: string;
  	change: string | null;
  	size?: "small" | "large";
  }

  export function ActionDisplay({ label, change, size = "small" }: ActionDisplayProps) {
  	// ...
  }

  // ХОРОШО: пропсы как объект, деструктуризация внутри
  interface Props {
  	label: string;
  	change: string | null;
  	size?: "small" | "large";
  }

  export function ActionDisplay(props: Props) {
  	const { label, change, size = "small" } = props;
  	// ...
  }

  // ХОРОШО: экспортируемые пропсы используют ComponentNameProps
  export interface ButtonProps {
  	variant: "primary" | "secondary";
  	onClick: () => void;
  }

  export function Button(props: ButtonProps) {
  	const { variant, onClick } = props;
  	// ...
  }
  ```

- **Границы переиспользования:** Общий компонент оправдан совпадающими ответственностью и поведением, а не только похожей разметкой. Если бизнес-сценарии различаются, сохраняйте отдельные композиции и переиспользуйте только совпадающие части; не скрывайте различия растущим набором режимов.
- **DI по необходимости:** Внедряйте зависимости на реальных границах вариативности или изоляции: например, один control с разными API загрузки. Composition выбирает adapter, а общий control не знает версию API. Обычно достаточно props с данными и функциями; не вводите DI-контейнер или интерфейс для каждого импорта. Чистые утилиты и стабильные доменные зависимости, которые не требуется подменять на этой границе, можно импортировать напрямую с соблюдением публичного API домена.
- **Минимальный контракт:** Передавайте только нужные данные и действия: например, `items`, `isLoading`, `onSelect` или `uploadMedia`. Не передавайте весь API client, service registry или результат query/mutation, если нужна лишь его часть. Узкий controller или query-state допустим, если это осмысленный контракт компонента. Для форм — [общий каталог контролов и разные API](forms.md#общий-каталог-контролов-и-разные-api).
- **Хуки не являются DI-параметрами:** Сам хук не передавайте через props/context и не выбирайте динамически (`useUpload={useLegacyUpload}`). Вызывайте его статически в компоненте или другом хуке, а через границу передавайте необходимые данные и обычные callbacks из результата. Локальные presentation-хуки вызывайте рядом с UI. Это соответствует [правилам React](https://react.dev/reference/rules/react-calls-components-and-hooks#dont-dynamically-use-hooks).
- **Смысловая связность:** Объединяйте controls по общей ответственности, а не потому, что они входят в один тикет, стоят рядом на экране или поддерживаются одним API. Например, настройки показа не относятся к регуляторным полям маркировки. Независимые блоки собирает владеющая сценарием composition.
- **Composition вместо множества boolean props:** Если компонент обрастает флагами, меняющими его структуру или режим работы, выделяйте явные варианты или используйте композицию.
- **Тонкие обёртки:** Допустимы, если выполняют конкретную роль: адаптируют control к форме или сохраняют единый контракт существующего каталога полей. Симметрия имён и гипотетическое будущее переиспользование сами по себе не оправдывают новый слой. Для компонента без UI обоснуйте отдельный lifecycle; не создавайте его только как место вызова side effect, если этим уже владеет существующий хук или lifecycle формы.
- **UX ownership:** UI-состояние должно принадлежать уровню, который владеет соответствующим пользовательским workflow. Если действие из одного раздела блокируется состоянием другого раздела, блокирующий UI (ошибка, подтверждение или guard) должен появляться рядом с причиной блокировки: переключите пользователя в нужный раздел, раскройте скрытый блок или сфокусируйте проблемный контрол до показа сообщения. Не размещайте сообщение, подтверждение или guard-flow там, где действие было нажато, если причина блокировки находится в другом контексте.
- **Новые переиспользуемые компоненты:** UI-компоненты без доменной семантики создавайте в дизайн-системе и добавляйте для каждого `*.stories.tsx` в том же diff. Переиспользуемые бизнес-компоненты и controls остаются в общем каталоге домена-владельца; несколько потребителей не делают их частью дизайн-системы. Владение общим кодом — в [features.md](features.md#владение-переиспользуемым-кодом).
- **Shared UI boundaries:** Не меняйте общий UI-слой (дизайн-систему) под частный сценарий приложения без серьёзной причины. Изменение shared UI допустимо, когда оно уточняет reusable-контракт компонента или исправляет общее поведение wrapper-а. App-specific flow, бизнес-правила и orchestration должны оставаться в `features/**`.
- **Условные React Query-хуки:** Для условного запуска `useQuery` и `useInfiniteQuery` используйте `skipToken` в `queryFn`, а не `enabled`. Это делает условие частью типизированного контракта запроса и избавляет от лишних состояний, когда хук смонтирован, но функция запроса формально всё равно существует.
  Правило относится к опциям запроса, а не к имени переменной: собственный хук может принимать boolean-условие и выбирать по нему `queryFn` или `skipToken`. Lint: собственное правило (запрет `enabled` в опциях запроса). `enabled: false` допустим для запроса, который запускают вручную через `refetch()`: с `skipToken` он падает.
- **Стабильные ссылки на коллекции в хуках:** Не используйте деструктуризацию с default `= []` / `= {}` для значений, которые попадают в deps `useMemo`, `useCallback` или в props таблицы (`data`, `columns`). Литерал создаёт новую ссылку на каждый render. Вынесите module-level константу и подставляйте через `??`:

  ```tsx
  const EMPTY_ITEMS: Item[] = [];

  const { data } = useQuery(...);
  const items = data ?? EMPTY_ITEMS;
  ```

  Апп-контракт таблиц — [tables.md](tables.md).

- **TanStack Form:** Обязательные правила submit, validation lifecycle, focus, reset и render stability находятся в [forms.md](forms.md). Не дублируйте form orchestration локальными обработчиками.
- **Presentation и чистые helpers:** Не передавайте `t` и `showToast` в чистые helpers. Передавайте данные, возвращайте результат или ключ перевода; переводы и side effects выполняйте в компоненте или хуке, который использует результат. Это не запрещает нейтральные данные или callbacks в явном DI-контракте компонента или orchestration-хука.

  ```tsx
  // ПЛОХО: проброс переводчика вместо локального presentation-хука
  interface Props {
  	t: (key: string) => string;
  	locale: string;
  }

  export function MyComponent(props: Props) {
  	const { t, locale } = props;
  	return <div>{t("hello")}</div>;
  }

  // ХОРОШО: переводы принадлежат компоненту, который их отображает
  interface Props {
  	// другие пропсы
  }

  export function MyComponent(props: Props) {
  	const t = useTranslations("MyNamespace");
  	const locale = useLocale();
  	return <div>{t("hello")}</div>;
  }
  ```

- **Optional props:** Задавайте default при деструктуризации, когда отсутствие значения означает обычное поведение компонента и эквивалентно этому default. Сохраняйте `undefined`, если оно является частью контракта: включает uncontrolled-режим, наследование настройки или отсутствие ограничения. Pass-through props вроде `className`, `children`, `id`, `aria-*` и optional callbacks также естественно остаются `undefined`.
- **`ReactNode` в props — крайность:** Не добавляйте `feedback?: ReactNode`, `extra?: ReactNode`, `banner?: ReactNode` и подобные «дырки» для произвольной разметки, если смысл данных известен. Предпочитайте типизированный контракт (`errorMessage?: string`, discriminated union, явный variant) и пусть **владеющий компонент** сам рисует системную разметку (токены, `role`, типографика). `ReactNode` / `children` допустимы для настоящей композиции (layout-слоты, обёртки, content, который вызывающий обязан собрать целиком) или когда набор вариантов заранее неизвестен и расширение API бессмысленно. Если caller вынужден собирать `<p className="text-fg-danger" role="alert">…</p>` снаружи — контракт слишком дырявый.
- **Вспомогательные функции:** Размещайте под компонентом, чтобы не отвлекать от основной логики.
- **Описание:** Для публичного API, сложной бизнес-логики, доступности/state machine логики и неочевидных алгоритмов обязательно краткое описание работы (JSDoc или комментарий в начале).
- **Структура компонента:** Придерживайтесь единого порядка внутри файла компонента для лучшей читаемости:
  1.  Объявление типов (`interface` / `type`).
  2.  Тело компонента.
      - Хуки (`useState`, `useContext`, `useRef`).
      - Хуки с логикой (`useEffect`, `useMemo`, `useCallback`).
      - Обработчики событий (`handleSomething`).
      - Вспомогательные рендер-функции (если есть).
      - `return` с JSX-разметкой.
  3.  Экспорт компонента.

## Доступность и композиция

- **Семантика сначала:** Для интерактивных действий используйте нативные элементы (`button`, `a`, `input`) или компоненты дизайн-системы поверх них. `div` с `onClick` допустим только для кастомных паттернов, где нативная семантика невозможна, и тогда обязательны role, keyboard support и focus-visible.
- **ARIA по назначению:** Добавляйте `aria-*` только когда это улучшает accessibility tree или описывает состояние, недоступное из нативной семантики. Не дублируйте нативные состояния без причины.
- **Клавиатура:** Кастомные интерактивные контролы должны поддерживать клавиатурное управление, видимый `focus-visible` и disabled/readOnly состояния, если они есть в API.
- **Context и composition:** Начинайте с явных props. Если промежуточные компоненты только передают их дальше, сначала рассмотрите композицию через `children`/slots; context используйте, когда эти способы неудобны для общего state/controller API. Несколько уровней передачи props сами по себе не требуют context. Контексты называйте по содержимому: `ComponentStateContext`, `ComponentProvider`, `useComponentStateContext`. Подробнее — [React: before you use context](https://react.dev/learn/passing-data-deeply-with-context#before-you-use-context).
- **Headless logic:** Выносите связанную state/interaction-логику в хук, когда это выделяет понятную ответственность, lifecycle или реальное переиспользование. Простое локальное состояние и обработчик могут оставаться в компоненте; отдельный хук на каждый control не нужен. Для синхронизации полей используйте существующий [lifecycle формы](forms.md#tanstack-form), не создавая второй путь управления состоянием.
