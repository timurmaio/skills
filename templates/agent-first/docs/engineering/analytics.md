# Продуктовая аналитика

[Карта инженерной документации](../../CODING_STANDARDS.md).

Canonical-схема продуктовых событий принадлежит системе аналитики (<PostHog, Amplitude, …>). Код приложения использует только публичную границу `@/lib/analytics`: `analyticsTrack`, `analyticsIdentify`, `analyticsSetUserProperties` и `analyticsReset`. Прямые вызовы SDK аналитики из доменов запрещены.

## Создание или изменение события

Работайте **сначала со схемой событий**, а не с TypeScript-файлами:

1. Проверьте, что существующее событие не покрывает сценарий. Выберите категорию по домену-владельцу из `src/features/` и имя по правилам ниже; зафиксируйте, какой факт наблюдает фронтенд и в какой момент отправляет событие. Контекст передавайте свойством `source` или другим описанным в схеме свойством, а не новым событием.
2. Создайте или обновите описание события в схеме: для каждого свойства — имя в `snake_case`, тип, обязательность, момент отправки и смысл значения. Boolean-ключи начинаются с `is_` или `has_`.
3. Получите типы из схемы (генератор или ручной тип в одном файле) и закоммитьте их. Generated-файл вручную не редактируют.
4. Вызовите `analyticsTrack` с canonical именем и payload. Имя и свойства проверяются типами из `@/lib/analytics`.

## Категория и имя события

Новые события используют формат `<category>:<object>_<completed_action>`, например `orders:creation_submitted` или `projects:creation_completed`. Не повторяйте объект, уже однозначно заданный категорией: `orders:order_creation_submitted` избыточно. Для действия над самой сущностью категории допустим формат `<category>:<completed_action>`, например `projects:deleted`. Каждая часть имени — lowercase `snake_case`; двоеточие отделяет категорию. Действие — в завершённой форме (`clicked`, `created`, `submitted`, `started`, `completed`).

Категория (namespace до двоеточия) обязана соответствовать домену-владельцу действия в `src/features/`. Имя категории выводится из имени папки домена: дефисы заменяются подчёркиваниями (`data-sources` → `data_sources`). Новую категорию вводят только для существующего домена проекта.

Выбирайте домен по принадлежности действия, независимо от страницы отправки: регистрация использует `auth:*`, а не `registration:*`. Названия сценариев и сокращения доменов не заменяют категорию домена. Объект описывает сущность, процесс или элемент интерфейса, а действие — наблюдаемый факт. Если категория охватывает несколько сценариев, имя после двоеточия явно указывает сценарий: `auth:registration_request_completed`.

Место отправки, провайдер, маршрут, язык и конкретное место входа не определяют категорию. Одно действие из нескольких мест использует одно событие; различия передаются в свойствах. Имена событий и свойств статичны: ID, URL и другие переменные значения передавайте в payload.

## Типы свойств и ограничения

- Одна property не может быть union разных базовых типов. Вместо `string | { min?: number; max?: number }` создайте отдельные однородные свойства и discriminator: `filter_type`, `filter_text`, `filter_min`, `filter_max`.
- Известный пустой набор передаётся пустым значением (`{ values: [] }` или `[]` по схеме), неприменимое или неизвестное свойство отсутствует.
- Событие без свойств вызывается только с именем: `analyticsTrack("support:help_clicked")`. Второй аргумент для него — ошибка типов.
- Одна пользовательская операция — одна пара событий «отправлено» и «завершено»; не дублируйте событие из нескольких слоёв.

## Проверка

Перед передачей изменений:

- описание события в схеме актуально, generated-типы пересобраны и закоммичены;
- новый вызов `analyticsTrack` и отправка проверены ближайшими unit-тестами;
- в browser verification событие видно в сети (метод, host и path) там, где его отправляет сценарий из AC.
