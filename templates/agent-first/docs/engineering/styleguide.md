## 1. Общие принципы

- **Границы изменения.** Не рефакторьте несвязанный код в том же diff.
- **Цена абстракции.** Новый слой должен упрощать понимание, изменение или проверку конкретного сценария. Указывайте, какую существующую ответственность или границу он выделяет; гипотетическое переиспользование не оправдывает универсальный framework.
- **Статус правил.** Именование и синтаксические предпочтения — командные соглашения ради единообразия, а не универсальное превосходство одного стиля. Архитектурные правила применяйте с указанными условиями, не превращая их в требования «DI везде» или «всё общее». Если правило мешает конкретному сценарию, предложите и согласуйте уточнение вместо молчаливого обхода.

## 3. Именование

- **Вложенные компоненты:** Добавляйте префикс модуля (например, `LayoutHeaderLink` вместо просто `Link` в модуле Layout) — это упрощает дебаг и поиск.
- **Описательность:** Имена должны быть ясными и отражать суть сущности. Избегайте сокращений и однобуквенных переменных (кроме итераторов в циклах). Используйте доменные термины: `columnMinSize` вместо `min`, `validatedSizes` вместо `result`.
- **Смысл, а не текущий transport:** Называйте общие capabilities, controls и business rules по назначению. То, что возможность пока поддерживает только один API, не делает её `Legacy`. Такой префикс уместен для действительно version-specific adapter, transport или оболочки маршрута.
- **Доменные термины:** В текстах, ключах переводов и внутренних идентификаторах используйте термин из `GLOSSARY.md` домена. Синоним из внешнего API, схемы, legacy-данных или стороннего сервиса допустим только на границе этого контракта.
- **Имена файлов:** Должны соответствовать основному экспорту: `MyComponent.tsx` для компонентов, `useDataFetching.ts` для хуков, `dataTransformers.ts` для утилит.
- **Константы:** Переменные-константы объявляйте через `UPPER_SNAKE_CASE` (например, `const SOME_CONSTANT = { ... };`).
- **Ключи browser storage:** Ключи для `localStorage`, `sessionStorage` и `cookie` именуйте в `kebab-case` с префиксом проекта `{{PROJECT}}-` (например, `"{{PROJECT}}-utm-notice-pending"` или `"{{PROJECT}}-statistics-table-columns-config"`). Имя JS-константы для такого ключа при этом остаётся в `UPPER_SNAKE_CASE`.
- **Search params приложения:** Новые ключи URL query именуйте в `camelCase`: `pageSize`, `accountId`, `copyFromItemId`, `copyMode`. Это соглашение для консистентности с существующими URL, а не техническое преимущество перед `kebab-case`.
- **Идентификаторы в search params:** Для идентификатора сущности используйте суффикс `Id`, для списка идентификаторов — `Ids`: `accountId`, `projectIds`, `copyFromItemId`. Имя отражает назначение: `copyFromItemId` — источник копирования, `copyMode` — режим копирования.
- **Значения режимов в search params:** Новые строковые значения перечислений именуйте строчными словами; несколько слов разделяйте дефисом: `bulk`, `add-source`. Произвольные пользовательские значения и идентификаторы не преобразуйте под этот стиль.
- **Внешние query-контракты и совместимость:** Имена и значения параметров API, OAuth и сторонних ссылок сохраняйте по внешнему контракту. Существующие URL приложения не переименовывайте только ради нового соглашения: изменение требует явного решения о совместимости.
- **Аббревиатуры:** В camelCase/PascalCase, а не ALL_CAPS внутри слова (например, `ApiEndpoint`, `HttpClient`, `CellUtm`; не `APIEndpoint`, `HTTPClient`, `CellUTM`).
- **"Следующий" vs "Новый":** Для переменных, которые представляют "следующий" массив/объект, вычисленный из предыдущего, используйте префикс `next` вместо `new`. Префикс `new` используется только для создания совершенно новых сущностей.

  ```tsx
  // ПЛОХО: new для "следующего" значения
  const newFilters = typeof updater === "function" ? updater(filters) : updater;
  const newSelection = updater(selection);

  // ХОРОШО: next для "следующего" значения
  const nextFilters = typeof updater === "function" ? updater(filters) : updater;
  const nextSelection = updater(selection);

  // ХОРОШО: new для создания новой сущности
  const newId = crypto.randomUUID();
  const newScenario = createEmptyScenario();
  ```

## 4. Компоненты (React)

- **Типизация Props:** Собственный объектный контракт `props` описывайте через `interface`. Интерфейс пропсов всегда должен называться `Props`, за исключением случаев, когда пропсы экспортируются (тогда используется `ComponentNameProps`). Производные контракты, unions и mapped/conditional types описывайте через `type` согласно [общему правилу TypeScript](#11-typescript).
- **Деструктуризация пропсов:** Пропсы всегда передаются как единый объект `props: Props`, а деструктуризация выполняется внутри функции. Lint: собственное правило проекта (запрет деструктуризации в параметрах компонента).
- **Изображения:** Используйте одну абстракцию изображений проекта (обычный `img`, компонент дизайн-системы или компонент фреймворка) — какую, решите один раз и запишите сюда.

  ```tsx
  // ПЛОХО: деструктуризация в параметрах
  interface ActionDisplayProps {
  	label: string;
  	change: string | null;
  	size?: "small" | "large";
  }

  export function ActionDisplay({ label, change, size = "small" }: ActionDisplayProps) {
  	// ...
  }

  // ХОРОШО: пропсы как объект, деструктуризация внутри
  interface Props {
  	label: string;
  	change: string | null;
  	size?: "small" | "large";
  }

  export function ActionDisplay(props: Props) {
  	const { label, change, size = "small" } = props;
  	// ...
  }

  // ХОРОШО: экспортируемые пропсы используют ComponentNameProps
  export interface ButtonProps {
  	variant: "primary" | "secondary";
  	onClick: () => void;
  }

  export function Button(props: ButtonProps) {
  	const { variant, onClick } = props;
  	// ...
  }
  ```

- **Границы переиспользования:** Общий компонент оправдан совпадающими ответственностью и поведением, а не только похожей разметкой. Если бизнес-сценарии различаются, сохраняйте отдельные композиции и переиспользуйте только совпадающие части; не скрывайте различия растущим набором режимов.
- **DI по необходимости:** Внедряйте зависимости на реальных границах вариативности или изоляции: например, один control с разными API загрузки. Composition выбирает adapter, а общий control не знает версию API. Обычно достаточно props с данными и функциями; не вводите DI-контейнер или интерфейс для каждого импорта. Чистые утилиты и стабильные доменные зависимости, которые не требуется подменять на этой границе, можно импортировать напрямую с соблюдением публичного API домена.
- **Минимальный контракт:** Передавайте только нужные данные и действия: например, `items`, `isLoading`, `onSelect` или `uploadMedia`. Не передавайте весь API client, service registry или результат query/mutation, если нужна лишь его часть. Узкий controller или query-state допустим, если это осмысленный контракт компонента. Для форм — [общий каталог контролов и разные API](forms.md#общий-каталог-контролов-и-разные-api).
- **Хуки не являются DI-параметрами:** Сам хук не передавайте через props/context и не выбирайте динамически (`useUpload={useLegacyUpload}`). Вызывайте его статически в компоненте или другом хуке, а через границу передавайте необходимые данные и обычные callbacks из результата. Локальные presentation-хуки вызывайте рядом с UI. Это соответствует [правилам React](https://react.dev/reference/rules/react-calls-components-and-hooks#dont-dynamically-use-hooks).
- **Смысловая связность:** Объединяйте controls по общей ответственности, а не потому, что они входят в один тикет, стоят рядом на экране или поддерживаются одним API. Например, настройки показа не относятся к регуляторным полям маркировки. Независимые блоки собирает владеющая сценарием composition.
- **Composition вместо множества boolean props:** Если компонент обрастает флагами, меняющими его структуру или режим работы, выделяйте явные варианты или используйте композицию.
- **Тонкие обёртки:** Допустимы, если выполняют конкретную роль: адаптируют control к форме или сохраняют единый контракт существующего каталога полей. Симметрия имён и гипотетическое будущее переиспользование сами по себе не оправдывают новый слой. Для компонента без UI обоснуйте отдельный lifecycle; не создавайте его только как место вызова side effect, если этим уже владеет существующий хук или lifecycle формы.
- **UX ownership:** UI-состояние должно принадлежать уровню, который владеет соответствующим пользовательским workflow. Если действие из одного раздела блокируется состоянием другого раздела, блокирующий UI (ошибка, подтверждение или guard) должен появляться рядом с причиной блокировки: переключите пользователя в нужный раздел, раскройте скрытый блок или сфокусируйте проблемный контрол до показа сообщения. Не размещайте сообщение, подтверждение или guard-flow там, где действие было нажато, если причина блокировки находится в другом контексте.
- **Новые переиспользуемые компоненты:** UI-компоненты без доменной семантики создавайте в дизайн-системе и добавляйте для каждого `*.stories.tsx` в том же diff. Переиспользуемые бизнес-компоненты и controls остаются в общем каталоге домена-владельца; несколько потребителей не делают их частью дизайн-системы. Владение общим кодом — в [features.md](features.md#владение-переиспользуемым-кодом).
- **Shared UI boundaries:** Не меняйте общий UI-слой (дизайн-систему) под частный сценарий приложения без серьёзной причины. Изменение shared UI допустимо, когда оно уточняет reusable-контракт компонента или исправляет общее поведение wrapper-а. App-specific flow, бизнес-правила и orchestration должны оставаться в `features/**`.
- **Условные React Query-хуки:** Для условного запуска `useQuery` и `useInfiniteQuery` используйте `skipToken` в `queryFn`, а не `enabled`. Это делает условие частью типизированного контракта запроса и избавляет от лишних состояний, когда хук смонтирован, но функция запроса формально всё равно существует.
  Правило относится к опциям запроса, а не к имени переменной: собственный хук может принимать boolean-условие и выбирать по нему `queryFn` или `skipToken`. Lint: собственное правило (запрет `enabled` в опциях запроса). `enabled: false` допустим для запроса, который запускают вручную через `refetch()`: с `skipToken` он падает.
- **Стабильные ссылки на коллекции в хуках:** Не используйте деструктуризацию с default `= []` / `= {}` для значений, которые попадают в deps `useMemo`, `useCallback` или в props таблицы (`data`, `columns`). Литерал создаёт новую ссылку на каждый render. Вынесите module-level константу и подставляйте через `??`:

  ```tsx
  const EMPTY_ITEMS: Item[] = [];

  const { data } = useQuery(...);
  const items = data ?? EMPTY_ITEMS;
  ```

  Апп-контракт таблиц — [tables.md](tables.md).

- **TanStack Form:** Обязательные правила submit, validation lifecycle, focus, reset и render stability находятся в [forms.md](forms.md). Не дублируйте form orchestration локальными обработчиками.
- **Presentation и чистые helpers:** Не передавайте `t` и `showToast` в чистые helpers. Передавайте данные, возвращайте результат или ключ перевода; переводы и side effects выполняйте в компоненте или хуке, который использует результат. Это не запрещает нейтральные данные или callbacks в явном DI-контракте компонента или orchestration-хука.

  ```tsx
  // ПЛОХО: проброс переводчика вместо локального presentation-хука
  interface Props {
  	t: (key: string) => string;
  	locale: string;
  }

  export function MyComponent(props: Props) {
  	const { t, locale } = props;
  	return <div>{t("hello")}</div>;
  }

  // ХОРОШО: переводы принадлежат компоненту, который их отображает
  interface Props {
  	// другие пропсы
  }

  export function MyComponent(props: Props) {
  	const t = useTranslations("MyNamespace");
  	const locale = useLocale();
  	return <div>{t("hello")}</div>;
  }
  ```

- **Optional props:** Задавайте default при деструктуризации, когда отсутствие значения означает обычное поведение компонента и эквивалентно этому default. Сохраняйте `undefined`, если оно является частью контракта: включает uncontrolled-режим, наследование настройки или отсутствие ограничения. Pass-through props вроде `className`, `children`, `id`, `aria-*` и optional callbacks также естественно остаются `undefined`.
- **`ReactNode` в props — крайность:** Не добавляйте `feedback?: ReactNode`, `extra?: ReactNode`, `banner?: ReactNode` и подобные «дырки» для произвольной разметки, если смысл данных известен. Предпочитайте типизированный контракт (`errorMessage?: string`, discriminated union, явный variant) и пусть **владеющий компонент** сам рисует системную разметку (токены, `role`, типографика). `ReactNode` / `children` допустимы для настоящей композиции (layout-слоты, обёртки, content, который вызывающий обязан собрать целиком) или когда набор вариантов заранее неизвестен и расширение API бессмысленно. Если caller вынужден собирать `<p className="text-fg-danger" role="alert">…</p>` снаружи — контракт слишком дырявый.
- **Вспомогательные функции:** Размещайте под компонентом, чтобы не отвлекать от основной логики.
- **Описание:** Для публичного API, сложной бизнес-логики, доступности/state machine логики и неочевидных алгоритмов обязательно краткое описание работы (JSDoc или комментарий в начале).
- **Структура компонента:** Придерживайтесь единого порядка внутри файла компонента для лучшей читаемости:
  1.  Объявление типов (`interface` / `type`).
  2.  Тело компонента.
      - Хуки (`useState`, `useContext`, `useRef`).
      - Хуки с логикой (`useEffect`, `useMemo`, `useCallback`).
      - Обработчики событий (`handleSomething`).
      - Вспомогательные рендер-функции (если есть).
      - `return` с JSX-разметкой.
  3.  Экспорт компонента.

## 5. Стилизация

- **Tailwind CSS:** Максимально используйте утилитарные классы Tailwind CSS для стилизации. Это основной подход.
- **Семантические токены цветов:** Для цветов в `className` — только semantic-токены дизайн-системы (например, `text-fg-*`, `bg-surface-*`, `border-stroke-*`). **Запрещено:** palette-классы (`text-zinc-*`, `bg-gray-*`), кастомные одноразовые `@theme`-цвета, hex/rgb в arbitrary values, если есть подходящий токен. Смысл цвета — из роли токена, не из оттенка palette.
- **Семантические токены типографики:** Для размера текста в `className` — только типографические токены дизайн-системы (например, `text-heading-*`, `text-body-*`, `text-caption`). **Запрещено:** `text-sm`, `text-xl`, `text-[Npx]` и другая шкала Tailwind. Storybook stories проверяются наравне с production UI.
- **Design-system компоненты и `className`:** У компонентов дизайн-системы `className` допустим только для внешнего layout-контекста: ширина, внешний отступ, позиционирование во flex/grid, `grow`/`shrink`, `self-*` и подобные контейнерные настройки. Через `className` нельзя переопределять их внешний вид: цвета, фон, border, radius, shadow, typography, внутренние отступы, hover/pressed/active-состояния.
- **Внутренний layout UI-компонента принадлежит компоненту:** В consumer-коде запрещено задавать через `className` самого UI-компонента классы, управляющие расположением его внутренних элементов: `flex-row`/`flex-col`, `grid-cols-*`, `gap-*`, `space-*`, `items-*`, `justify-*`, `flex-wrap` и аналогичные. Типизированный prop/variant (`layout`, `orientation`, `density`) добавляйте только при появлении реального повторяющегося consumer-сценария, а не заранее; до этого не обходите контракт через произвольный CSS.
- **Не добавляйте `*ClassName` для внутренних частей UI-компонента:** Не расширяйте API дизайн-системы пропсами вроде `listClassName`, `contentClassName`, `triggerClassName`, `iconClassName`, если они дают потребителю менять layout или внешний вид внутренних DOM-узлов. Обычно допустим максимум один корневой `className` для позиционирования компонента в родительском layout. Размеры, плотность, ориентацию и другие устойчивые варианты оформляйте через явные props/variants.
- **Внешний вид компонентов через API:** Размер, вариант, тон и другие визуальные состояния задавайте через `size`, `variant` и другие явные props/variants компонента. Если нужного варианта нет, сначала расширяйте API компонента, а не обходите его через `className`.
- **Slots не обходят дизайн-систему:** Не подменяйте стандартные внутренние элементы UI-компонента собственной разметкой через `children`/slots ради другого размера, отступов или внешнего вида. Например, для обычной иконки кнопки используйте `leftIcon`/`rightIcon`, а не slot с вручную стилизованной иконкой. Slots — для содержимого, отличающегося по смыслу от стандартного элемента, например аватара или badge.
- **Ширина модальных окон только через `size`:** Для диалогов запрещено переопределять ширину через `className` или arbitrary-классы вроде `max-w-[560px]`. Используйте ближайший существующий вариант `size`; новый вариант добавляйте только для повторяющегося продуктового размера, а не для единичного макета.
- **Инлайн-стили:** Статическое оформление задавайте через Tailwind или CSS Modules. Атрибут `style` допустим для runtime-значений, которые нельзя выразить конечным набором классов: вычисляемых размеров и координат, CSS custom properties, параметров анимации, style-контрактов библиотек (размеры колонок, виртуализация). Инлайн-стили не должны обходить semantic-токены, variants или другой публичный API дизайн-системы.
- **CSS Modules:** Используйте файлы `.module.css` в тех редких случаях, когда Tailwind не подходит. Например, для сложных анимаций или стилей, зависящих от множества динамических состояний.
- **tailwind-variants:** Для компонентов с несколькими визуальными состояниями используйте `tailwind-variants`, а не сборку длинных условных строк в JSX. Boolean variants называйте в стиле render-state: `isSelected`, `isDisabled`, `isHovered`, `isFocused`, `isPressed`. Файл со стилями называйте рядом с компонентом, например `Component.styles.ts`.
- **Семантические HTML-теги для текста:** Для текстовых блоков используйте семантические теги `p` (параграф) или `span` (инлайн-текст), а не `div`. Это улучшает доступность и семантику разметки.

  ```tsx
  // ПЛОХО: palette и шкала Tailwind вместо токенов
  <p className="text-sm text-zinc-500">Описание функции</p>

  // ХОРОШО: p + semantic-токены
  <p className="text-body-medium text-fg-subtle">Описание функции</p>

  // ХОРОШО: span для инлайн-текста
  <span className="text-body-medium text-fg-subtle">Дополнительная информация</span>
  ```

## 6. Логика и Функции

- **Объявление функций:** Функции уровня модуля объявляйте через `function` (`function doSomething() { ... }`): это обеспечивает hoisting и упрощает отладку в стеке вызовов. Lint: `func-style: ["error", "declaration", { allowTypeAnnotation: true }]` — переменную с явным типом функции (`const handler: Handler = () => ...`) он не трогает. Стрелочные функции внутри компонентов и хуков — норма.
- **Чистота функций:** Стремитесь писать чистые функции, которые не имеют побочных эффектов и возвращают одинаковый результат при одинаковых входных данных.
- **Параметры функций:** Объявляйте обязательный объект входных параметров через интерфейс `Params`. Для объекта настроек поведения используйте `Options`, если большинство полей optional/defaultable или объект расширяется как конфигурация. Optional параметры должны иметь дефолтные значения. Исключение: если у функции один примитивный параметр, интерфейс можно не объявлять.
- **Неиспользуемые параметры:** Если параметр не используется, удаляйте его из сигнатуры. Не оставляйте заглушки вроде `_error`, `_event`, `_value`, если колбэк или функция корректно работают без них.
- **useCallback:** Не добавляйте `useCallback` автоматически. Используйте его только когда есть понятная причина: мемоизированный дочерний компонент, стабильная зависимость для эффекта, подписка/отписка на event listener или другая логика, чувствительная к ссылочной идентичности.
- **Избегайте `else if`:** Используйте `else if` только в крайних случаях. Предпочитайте ранние возвраты (`early return`) или отдельные `if` блоки для улучшения читаемости. Lint: `no-else-return`.

  ```tsx
  // ПЛОХО: цепочка else if с ранними возвратами
  if (condition1) {
  	return value1;
  } else if (condition2) {
  	return value2;
  } else if (condition3) {
  	return value3;
  }
  return defaultValue;

  // ХОРОШО: ранние возвраты без else if
  if (condition1) {
  	return value1;
  }
  if (condition2) {
  	return value2;
  }
  if (condition3) {
  	return value3;
  }
  return defaultValue;
  ```

  **Исключение:** Если `return` у вас один и только после проверки всех условий, то `else if` допустим:

  ```tsx
  // ХОРОШО: один return в конце, else if допустим
  let result;
  if (condition1) {
  	result = value1;
  } else if (condition2) {
  	result = value2;
  } else if (condition3) {
  	result = value3;
  } else {
  	result = defaultValue;
  }
  return result;
  ```

  ```tsx
  // ПЛОХО: useCallback без причины
  const handleClick = useCallback(() => {
  	onClick(data);
  }, [onClick, data]);

  // ХОРОШО: простая функция без мемоизации
  function handleClick() {
  	onClick(data);
  }

  // ХОРОШО: useCallback, когда стабильная ссылка действительно нужна
  const handleClick = useCallback(() => {
  	setCount((prev) => prev + 1);
  }, []);
  ```

## 7. Доступность и композиция

- **Семантика сначала:** Для интерактивных действий используйте нативные элементы (`button`, `a`, `input`) или компоненты дизайн-системы поверх них. `div` с `onClick` допустим только для кастомных паттернов, где нативная семантика невозможна, и тогда обязательны role, keyboard support и focus-visible.
- **ARIA по назначению:** Добавляйте `aria-*` только когда это улучшает accessibility tree или описывает состояние, недоступное из нативной семантики. Не дублируйте нативные состояния без причины.
- **Клавиатура:** Кастомные интерактивные контролы должны поддерживать клавиатурное управление, видимый `focus-visible` и disabled/readOnly состояния, если они есть в API.
- **Context и composition:** Начинайте с явных props. Если промежуточные компоненты только передают их дальше, сначала рассмотрите композицию через `children`/slots; context используйте, когда эти способы неудобны для общего state/controller API. Несколько уровней передачи props сами по себе не требуют context. Контексты называйте по содержимому: `ComponentStateContext`, `ComponentProvider`, `useComponentStateContext`. Подробнее — [React: before you use context](https://react.dev/learn/passing-data-deeply-with-context#before-you-use-context).
- **Headless logic:** Выносите связанную state/interaction-логику в хук, когда это выделяет понятную ответственность, lifecycle или реальное переиспользование. Простое локальное состояние и обработчик могут оставаться в компоненте; отдельный хук на каждый control не нужен. Для синхронизации полей используйте существующий [lifecycle формы](forms.md#tanstack-form), не создавая второй путь управления состоянием.

## 8. Комментарии

- **Говорящие названия** имеют приоритет над комментариями. Комментируйте только сложную логику.
- **Комментируем "почему", а не "что":** Не описывайте очевидные вещи. Объясняйте, почему было выбрано именно такое, возможно, нетривиальное решение.
- **Сложная логика:** Обязательно комментируйте сложные алгоритмы, бизнес-логику или временные "костыли".
- **Стиль:** `//` для однострочных, `/** ... */` для JSDoc. Пишите полными предложениями: заглавная буква, точка в конце.
- **JSDoc:** Подробный — у основной экспортируемой сущности. Краткий — у внутренних функций, где когнитивно сложно. Описывайте «зачем», не «что делает».
- **TODO-комментарии:** Для отслеживания технического долга используйте структурированный формат.
  - **Формат:** `// TODO: [TICKET-123] Описание задачи, которую нужно выполнить.`

### Примеры

```ts
// ПЛОХО: избыточный JSDoc
interface Options {

// ХОРОШО: обычный комментарий
interface Options {
	// Уникальный ключ для сохранения состояния в localStorage.

}

// ПЛОХО: неочевидные имена

	if (v > 0) result[k] = v;

// ХОРОШО: понятно благодаря именованию

	if (size > 0) validatedSizes[columnId] = size;
```

## 9. Тесты

- **Язык тест-кейсов:** Описания `describe`, `it` и `test` пишутся на русском языке: тесты в репозитории — на одном языке. Название из одного токена — имя кода (`describe("Select")`) — допустимо.
- **Формулировка:** Названия тестов описывают наблюдаемое поведение системы, а не детали реализации.
- **Селекторы:** Предпочитайте `getByRole` и `getByLabelText`. `getByText` допустим для проверки видимого текстового содержимого, например summary, статуса или сообщения.
- **Поведение вместо реализации:** Проверяйте пользовательский результат, ARIA-состояния и доступную семантику, а не CSS-классы и внутренние детали компонента.

## 10. Переводы (i18n)

- **Ключи переводов:** Сегменты namespace используют `PascalCase` (например, `Accounts` или `UI.MultiSelect`), а конечные message keys — `kebab-case` (например, `"error-message"`, `"user-name"`). Одинаковый набор ключей во всех локалях должна проверять команда в `pnpm check`.
- **Структура:** Один namespace соответствует одной согласованной области переводов и подключается под одним и тем же именем везде. Переводы для заголовков страниц используют ключ `title`. Детали интеграции домена — в [features.md](features.md#интеграции-домена).
- **Маппинг API ошибок:** При работе с ошибками из API (которые могут быть в `PascalCase` или другом формате) необходимо сначала создать маппинг на ключи переводов в `kebab-case`, а затем использовать эти ключи в файлах переводов. Сырой текст ошибки API (`detail`, `message`) в интерфейс не выводится.

  ```tsx
  // ПЛОХО: прямое использование API ошибки как ключа перевода
  const errorKey = `logs.errors.${errorType}`; // errorType = "UnknownError"

  // ХОРОШО: маппинг API ошибок на kebab-case ключи с as const
  const ERROR_TYPE_TO_TRANSLATION_KEY = {
  	UnknownError: "unknown-error",
  	UpstreamUnavailableError: "upstream-unavailable-error",
  } as const satisfies Record<ActionLogErrorType, string>;
  const translationKey = ERROR_TYPE_TO_TRANSLATION_KEY[errorType];
  const errorKey = `logs.errors.${translationKey}`;
  ```

## 11. TypeScript

- **interface vs type:** Собственные plain-object контракты, включая props, объявляйте через `interface`. Unions, tuples, primitives, mapped/conditional types и контракты, производные через utility types, объявляйте через `type`. Не создавайте пустой или искусственный `interface` только ради запрета `type`.
- **Import types:** Используйте `import type` для импорта только типов. Для смешанных импортов: `import { type SomeType, fooBar } from "module"`.
- **React-типы:** Не используйте неймспейсные типы вида `React.ReactNode`. Для React-типов используйте отдельные type-импорты (например, `import type { ReactNode } from "react"`).

## 12. Утилиты и кейсы

- **Переиспользование:** Перед созданием helper проверьте `src/utils`, домен-владелец и уже установленные библиотеки, в том числе `es-toolkit`. Не дублируйте подходящую по контракту функцию. Место новой утилиты определяйте по [доменной ответственности](features.md#владение-переиспользуемым-кодом), а не по количеству потребителей.
- **Проверка конечности числа:** Для проверки, что значение — конечное число (не ±`Infinity` и не `NaN`), используйте `Number.isFinite(value)`. Оно не преобразует входящее значение к числу. То же для `Number.isNaN`; Lint: `no-restricted-globals` для `isFinite` и `isNaN`.
- **HTTP-статус ошибки API:** Статус ошибки запроса читается одним helper из `src/api/helpers`, а не разбирается на месте (`x.response.status`, текст ошибки). Закрепите это lint-правилом, которое называет helper в сообщении.
- **React Aria:** Компоненты и хуки React Aria импортируйте с `Aria`-алиасом, если имя может конфликтовать с компонентами проекта: `import { Button as AriaButton } from "react-aria-components";`. Это помогает отличать внешние primitives от UI-компонентов проекта.
- **Select-подобные компоненты React Aria:** В UI-обёртках проекта используйте `value` и `onChange` вместо `selectedKey` и `onSelectionChange`, чтобы API был согласован с обычными form-контролами. При `selectionMode="multiple"` `value` и `onChange` принимают массив.

## 13. Type Assertions

- **Избегайте type assertions:** Type assertions (`as Type`) должны использоваться только в крайнем случае, когда TypeScript не может автоматически вывести правильный тип, и нет другого способа решить проблему.
- **Предпочитайте выведение и проверку типов:** Используйте `as const`, `satisfies`, type guards и другие механизмы TypeScript вместо assertions. Helper безопаснее assertion только тогда, когда действительно доказывает контракт статически или проверяет значение в runtime; перенос `as Type` внутрь функции не делает код безопаснее.

### Пример

```tsx
// ПЛОХО: ненужный type assertion
const value = someFunction() as MyType;

// ХОРОШО: использование as const для выведения типа
const ERROR_MAP = {
	key1: "value1",
	key2: "value2",
} as const;

// ХОРОШО: type guard проверяет значение до сужения типа
const MY_TYPE_VALUES = ["key1", "key2"] as const;
type MyType = (typeof MY_TYPE_VALUES)[number];

function isMyType(value: string): value is MyType {
	return MY_TYPE_VALUES.some((candidate) => candidate === value);
}
```
