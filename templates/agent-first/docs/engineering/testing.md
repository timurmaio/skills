## Testing strategy и upstream TDD

Код меняем по `test-driven-development`: тест сначала, для фич, багфиксов, рефакторинга и изменений поведения. Так требуют оба upstream — Superpowers и `implement` Мэтта.

Исключения — как в самом skill: throwaway prototype, сгенерированный код, конфиги; плюс docs. Ещё одно исключение может задать ticket или пользователь — в поле `Testing strategy` с причиной, например `browser-only — правка вёрстки, логики нет`. Без такой записи «тесты потом» не выбирай.

- Test seams, записанные в ticket/spec, считаются pre-agreed. Если seams не определены, согласуйте их до первого test.
- Пользователь недоступен, а seams не записаны — выбери их сам по этому документу и запиши решение в итоговый отчёт.
- Правила ниже дополняют upstream skill: как запускать тесты и что считать red у нас.
- Команды — в [verification.md](verification.md#команды); форматирование делает pre-commit hook.
- Ошибка импорта или компиляции — ещё не red: тест должен упасть на проверке поведения.
- Тест, который сразу зелёный, не удаляй. Сначала объясни, почему он прошёл; затем временно сломай код и убедись, что тест падает. Так ловятся скрытые баги и тесты, которые не могут упасть.
- `it.each` — один тест на строку таблицы: каждая строка проходит свой red → green.
- Решения, которые закрепляешь тестом вместо владельца, перечисли в отчёте отдельным списком «вопросы владельцу».

## Что тестировать

- Чистые функции, нетривиальную логику и доменные границы.
- Boundary cases для форматтеров и utils с явными границами диапазонов.
- Pure-функцию, вызвавшую UI-баг: тест обязателен на уровне функции.
- Не добавляйте regression-тесты на простой UI-render и очевидный wiring, если сценарий быстро и надёжно проверяется QA; такое исключение из TDD записывай в `Testing strategy` ticket.
- Storybook-only код по умолчанию не тестируйте.
- Регрессионный тест на баг сначала падает на старом коде — по той причине, что в баге, — и проходит после исправления. Оба запуска покажите в отчёте: тест, который проходил и до исправления, баг не ловит.
- Лучше без нового теста, чем с плохим. Если тест получается только на моках, на деталях реализации, на тайминге или с дорогой инфраструктурой ради мелкого фикса, возьмите ближайшую исполняемую проверку — скрипт или сценарий в браузере — и укажите в отчёте, почему теста нет.

## Ценность теста

Новый или изменённый тест отвечает на четыре вопроса. Нет конкретного ответа — тест не нужен.

1. **Контракт.** Какое наблюдаемое поведение, инвариант или внешний контракт (API, формат данных) он защищает?
2. **Регрессия.** Какая правдоподобная правка кода его уронит?
3. **Главный тест.** Почему эту регрессию не ловят существующие тесты? У контракта один главный тест — на самой сильной границе, где контракт виден. Таблица случаев чистой функции живёт в её тесте; форма или компонент, который её использует, проверяет свою обвязку одним случаем. Новый случай — строка в таблице главного теста, а не ещё один тест слоем выше.
4. **Шов.** Нужен ли ради теста экспорт, флаг или параметр, которого нет у продакшен-вызова? Тогда проверяйте через настоящую границу, а шов не добавляйте.

## Пустой тест

Пустой тест зелёный при любой реализации: он не может упасть, поэтому ничего не защищает. Признаки:

- Мок сам поставляет проверяемое поведение: мок `mutate` не вызывает `onError`, а тест называется «ошибка отправки оставляет модалку открытой».
- Название обещает то, чего проверки не касаются: «очищает адрес», а проверяется только тело запроса, которое и без очистки собирается из выбранного способа доставки.
- Отрицательная проверка проходит не на той защите: запрос «не ушёл», потому что форма невалидна по другому полю.
- Тавтология: ожидаемое значение повторяет реализацию — `expect(TITLE_MAX_LENGTH).toBe(160)`, значение, посчитанное той же формулой, что и в коде, или копия списка из конфига. Ожидаемое значение берите из независимого источника: требования, примера, известного литерала.
- Проверяется форма вызова (`expect.objectContaining({ onSuccess: expect.any(Function) })`) вместо результата, хотя вызов — не публичный контракт.

Подозрение подтверждайте **мутацией**: временно сломайте код, который тест защищает, и запустите тест. Остался зелёным — тест пустой. После прогона верните файл (`git checkout -- <path>`) и проверьте, что `git status` его не показывает. Починенный тест падает на той же мутации.

## Аудит тестов

Аудит — разбор существующих тестов по просьбе пользователя: «проверь, все ли тесты нужны». Ревью diff проверяет только новые и изменённые тесты — по [ценности](#ценность-теста) и [признакам пустого теста](#пустой-тест). Процедура — сокращённый upstream `openclaw/test-audit`: сам skill завязан на скрипты и документы openclaw, поэтому не подключён.

1. **Scope.** Файлы или домен и число тестов до правок.
2. **Пометки.** Прочитайте каждый тест целиком, его продакшен-код и другие тесты того же кода. Каждому `it` — или строке `it.each`, если строкам нужны разные пометки, — поставьте одну:
   - `R` — оставить: назовите контракт и регрессию;
   - `F` — починить проверку: тест пустой, мутация это подтвердила;
   - `C` — слить: назовите главный тест, который заберёт проверку;
   - `D` — удалить: назовите тест, который продолжит доказывать контракт, или почему контракта нет.

   Судите по проверкам, а не по названию. Тест из фикса бага (`git log -S "<название теста>"`) — регрессия: удаляйте его, только если тот же баг ловит другой тест. Медленный тест — не причина удалять. Красный тест может быть багом продукта: сначала `systematic-debugging`.

   **Done when:** у каждого теста пометка и строка доказательства.

3. **Решение.** До правок покажите пользователю `F`, `C`, `D` с доказательствами, `R` — числом.
4. **Правки.** Каждый `F` падает на своей мутации; число тестов после правок — исходное минус `D` и слитые `C`.

## Селекторы

Иерархия предпочтений:

1. `getByRole` — лучший выбор для большинства UI-сценариев.
2. `getByLabelText` — для форм и полей ввода.
3. `getByTestId` — для кастомных компонентов без стабильной семантической роли.
4. `getByText` — только для проверки текстового содержимого.
5. `getByPlaceholderText` — только для полей ввода.
6. `container.querySelector` — избегать, использовать только в крайних случаях.

```typescript
// Хорошо: семантически точный селектор.
screen.getByRole("button", { name: "Развернуть" });
screen.getByRole("treeitem", { name: "Элемент 1" });

// Плохо: поиск только по тексту, когда доступна роль.
screen.getByText("Развернуть");
screen.getByText("Элемент 1");
```

## Behavior vs Implementation

Тестируйте поведение, которое важно пользователю, а не внутренние детали реализации.

```typescript
// Хорошо: проверяем результат действия.
it("пользователь может развернуть узел", async () => {
	render(<TreeExample items={data} />);
	await user.click(screen.getByRole("button", { name: "Развернуть" }));
	expect(screen.getByRole("treeitem", { name: "Дочерний элемент" })).toBeVisible();
});

// Плохо: тест привязан к внутреннему callback contract без пользовательского результата.
it("вызывает onExpandedChange с правильными параметрами", () => {
	const onExpandedChange = vi.fn();
	render(<TreeExample onExpandedChange={onExpandedChange} />);
	expect(onExpandedChange).toHaveBeenCalledWith(expect.any(Set));
});
```

## Accessibility

Для UI-тестов предпочитайте роли и проверяйте важные ARIA-состояния.

```typescript
const item = screen.getByRole("treeitem", { name: "Элемент 1" });

expect(item).toHaveAttribute("aria-selected", "true");
expect(item).toHaveAttribute("aria-expanded", "false");
expect(item).toHaveAttribute("aria-disabled", "true");
```

## Устойчивость

- Используйте regex там, где точный текст делает тест хрупким.
- Не проверяйте CSS classes, если можно проверить пользовательское поведение или accessibility state.
- Группируйте похожие проверки через `it.each`.

```typescript
screen.getByRole("treeitem", { name: /Элемент/ });
screen.getByRole("button", { name: /Развернуть|Свернуть/ });
```

## Структура

Используйте Arrange, Act, Assert:

```typescript
it("пользователь может выбрать элемент", async () => {
	render(<TreeExample items={data} />);

	await user.click(screen.getByRole("treeitem", { name: "Элемент 1" }));

	expect(screen.getByRole("treeitem", { name: "Элемент 1" })).toHaveAttribute("aria-selected", "true");
});
```

## Time-Based Tests

Не используйте `performanceUtils`, ручные измерения времени и жёсткие лимиты времени в тестах.

```typescript
// Плохо: результат зависит от скорости окружения.
const result = performanceUtils.measureTime(() => {
	render(<Component items={largeData} />);
}, 1000);
expect(result.isWithinLimit).toBe(true);

// Хорошо: проверяем стабильность и корректность результата.
expect(() => {
	render(<Component items={largeData} />);
}).not.toThrow();
```

## Моки и callbacks

Проверяйте результат для пользователя. Проверку вызовов используйте только когда callback и есть публичный контракт компонента или helper.

```typescript
// Хорошо.
await user.click(screen.getByRole("button", { name: "Сохранить" }));
expect(screen.getByText("Сохранено")).toBeVisible();

// Часто плохо.
expect(mockSaveFunction).toHaveBeenCalledWith(data);
```

## Имена тестов

Имена тестов должны описывать поведение с точки зрения пользователя или домена.

```typescript
it("пользователь может развернуть узел при клике на chevron");
it("отключает недоступные элементы");
it("поддерживает множественный выбор");
```

## Custom Hooks

Кастомные хуки обычно тестируйте через компонент, который использует хук. Тестировать hook напрямую стоит только если сам hook является публичной headless-абстракцией и поведение нельзя надёжно проверить через UI.

```typescript
function TestComponent() {
	const { data, loading } = useCustomHook();
	return loading ? <div>Загрузка...</div> : <div>{data}</div>;
}
```

## Чеклист

- [ ] Используются `getByRole` вместо `getByText` где возможно.
- [ ] Тесты описывают поведение, а не implementation details.
- [ ] Важные ARIA/state атрибуты проверяются через доступную семантику.
- [ ] Нет time-based тестов.
- [ ] CSS classes не проверяются без необходимости.
- [ ] Моки проверяются только там, где вызов является важным контрактом.
- [ ] Имена тестов понятны и описывают сценарий.
- [ ] Новый или изменённый тест отвечает на вопросы [ценности](#ценность-теста); подозрение на [пустой тест](#пустой-тест) проверено мутацией.
