## Validation lifecycle

Для create/edit-форм используйте lazy validation:

1. До взаимодействия не показывайте required-ошибки только из-за пустого initial state.
2. На `change` и `blur` можно обновлять состояние и показывать ошибку по принятой политике формы, но нельзя автоматически переносить фокус.
3. На submit запускайте полную клиентскую валидацию.
4. Если submit отклонён, покажите все актуальные ошибки и переведите фокус на первую из них.
5. После первой попытки submit допускается live-пересчёт уже показанных ошибок. Исправление значения может убрать ошибку, но не должно само переводить фокус.

Доменная форма может валидировать отдельное поле раньше, если без этого невозможно продолжить конкретный flow. Такое поведение должно быть локальным и не менять общий submit/focus lifecycle.

## Фокус после отклонённого submit

### Обязательное поведение

Каждая отклонённая попытка submit заново находит **первый актуальный невалидный контрол** в пользовательском порядке формы:

- первый submit при пяти пустых required-полях фокусирует поле №1;
- ввод в поле №1 не вызывает автофокус и не меняет текущий фокус;
- следующий submit повторяет тот же поиск; поскольку поле №1 уже валидно, фокус получает поле №2;
- повторный submit без исправления поля №2 снова фокусирует поле №2.

Иными словами, алгоритм не хранит cursor и не помнит предыдущую ошибку. Изменяется набор невалидных контролов, а не стратегия поиска.

### Реализация

- Запускайте перенос фокуса только из `onSubmitInvalid` или эквивалентного события отклонённого submit.
- Ограничивайте поиск текущей формой, dialog или логической секцией, а не всем `document`.
- Используйте общий `useFocusFirstInvalidControl` из field-модуля дизайн-системы.
- Планируйте focus после commit с ошибками и отменяйте устаревшую запланированную попытку.
- Пропускайте disabled, скрытые и нефокусируемые цели.
- Фокусируйте с `preventScroll`, затем используйте `scrollIntoView({ block: "nearest", inline: "nearest" })`.

```tsx
const formRef = useRef<HTMLFormElement>(null);
const focusFirstInvalidControl = useFocusFirstInvalidControl(formRef);

const form = useForm({
	onSubmitInvalid: focusFirstInvalidControl,
});
```

### Tabs, accordions и несмонтированные секции

Первой считается ошибка в пользовательском порядке всей формы, даже если её контрол сейчас скрыт в tab или accordion:

1. Определите первый невалидный контейнер в порядке секций.
2. Откройте или смонтируйте этот контейнер.
3. После commit сфокусируйте первый невалидный контрол внутри него.

Активная секция не является cursor. Повторный submit без исправлений должен привести к той же первой ошибке, а не к следующей секции.

Для длинной формы можно дополнительно добавить сводку ошибок со ссылками на поля. Она дополняет, но не заменяет focus-навигацию и корректную разметку контролов.

## Разметка ошибок

ARIA-контракт подробно описан в [accessibility.md](accessibility.md#ошибки-формы-и-focus-targets).

### Владелец ошибки

- Полноценный field-компонент владеет своим label, control, description и error layout. Он принимает единообразные `isInvalid`, `errorMessage` и, когда применимо, `description`, сам отображает сообщение и связывает его с фокусируемым контролом.
- Форма вычисляет и передаёт validation state, но не дорисовывает `StandaloneError` рядом с готовым field-компонентом. Иначе легко получить дублирование сообщения и две конкурирующие ARIA-связи.
- Низкоуровневые primitives (`Input`, отдельный `Radio`, trigger/button) не обязаны владеть сообщением. Ошибка принадлежит ближайшему компоненту уровня field: например, `RadioGroup`, `Select` или feature-композиту.
- Feature-композит, собранный не из готового field-компонента, отображает `StandaloneError` внутри собственной границы. Примеры: upload-контрол, кнопка открытия редактора расписания или dialog-based generator.
- Для submit-ошибки, связанной с recovery action через `aria-describedby` и последующий focus, используйте `StandaloneError isLive={false}`. Режим alert оставляйте самостоятельным ошибкам, после появления которых фокус не переносится.
- Ошибка загрузки данных может быть standalone, если сам control не рендерится и пользователю недоступно действие исправления значения.

Кратко:

- value-owning контрол выставляет `aria-invalid="true"` на своём фокусируемом элементе;
- контрол связывается с текстом ошибки через `aria-describedby` или нативный механизм field-компонента;
- составной контрол помечает реальную focusable recovery action через условный `data-invalid-focus-target="true"`;
- action button не получает `aria-invalid` только ради технического поиска;
- сообщения получают уникальные `id` через `useId`.

## TanStack Form

- Отправляйте форму через `form.handleSubmit()` и `onSubmit` HTML-формы. Не вызывайте mutation handler отдельно из UI-кнопки.
- Используйте `onSubmitInvalid` как единую точку submit-only навигации по ошибкам.
- Связанные поля синхронизируйте через `listeners`, а не через разрозненные `setFieldValue` в нескольких `onChange`.
- Если форма остаётся смонтированной между открытиями dialog или сменой редактируемой сущности, выполняйте один явный `form.reset(...)` в точке открытия/смены контекста.
- `submissionAttempts` можно использовать для включения live-валидации после первой попытки, но не как cursor для навигации по ошибкам.
- Form-level validator должен возвращать ошибки, а не менять React/form state во время render.

## Общий каталог контролов и разные API

Если версии формы имеют одинаковые ответственность и поведение и отличаются только backend API, используйте общие controls и fields. Версия API определяется в orchestration/composition-слое формы. Похожая разметка при разных бизнес-сценариях не требует единой реализации.

- Не создавайте параллельные `Legacy`/`V2`-версии одного контрола и не добавляйте в общий control флаги вроде `legacy`, `source="legacy"` или проверки версии API.
- Общий control получает минимальный нейтральный контракт: нужные значения, callbacks, loader/controller или query-state. Он не импортирует version-specific API hook, mapper или parser. Применяйте [правила DI и хуков](react.md#компоненты-react): сам хук не передаётся как зависимость.
- Composition выбирает нужный API adapter и передаёт его общему control. Version-specific mapper, query keys и transport hook остаются в своей API-оболочке; необходимость response parser определяется [политикой границ данных](features.md#границы-данных), а не наличием adapter.
- Доменный control может находиться в общем каталоге, даже если пока используется одной версией формы. Реализуйте текущий контракт без запасных режимов, фиктивных adapters и параметров под будущий API. Отсутствие второго потребителя не требует ни привязки UI к transport, ни преждевременной универсализации.
- Отдельные Views и секции-композиции для разных пользовательских flow допустимы. Совпадающие fields и business rules переиспользуются; реально различающиеся поведение, validation или lifecycle остаются в соответствующем сценарии и не маскируются API-флагами общего control.

```tsx
<OrderFormSimilarItemsControl
	form={form}
	field="items"
	accountId={accountId}
	loadSimilarItems={fetchOrdersV1SimilarItems}
/>
```

## Async validation и server errors

### Блокировка действий на время проверок

Для форм, модальных окон и пошаговых сценариев:

- Пока идёт хотя бы одна релевантная проверка текущих значений и контекста, блокируйте переход (включая предпросмотр)/submit через `Button.isPending={isSubmitting || isValidating}`. Учитывайте связанные и общие поля, все строки пачки; несвязанные фоновые загрузки не блокируют действие.
- После проверок ошибки сами по себе кнопку не блокируют: нажатие показывает актуальные ошибки и фокусирует первую. Не привязывайте блокировку к `isValid`/`canSubmit`.
- Обработчик перехода/submit также проверяет актуальное состояние ожидания: клавиатура и быстрый клик до обновления UI не должны обходить блокировку.
- Разрешайте переход только с полным актуальным результатом. Отмена, ошибка или устаревший результат не считаются успехом; при отмене или устаревшем результате сохраняйте ввод. Не откладывайте заблокированный клик для автоматического перехода; submit, сам запустивший проверку, может продолжиться после её успеха.
- Ожидание показывайте в интерфейсе, без тоста «Подождите». Выбор состояния кнопки, фокус и объявления → [accessibility.md](accessibility.md#асинхронная-проверка-и-disabled-действия).

### Отправка и ошибки сервера

- Не запускайте одинаковую async-проверку параллельно из field handler и submit pipeline.
- Защищайте async submit от повторной отправки через единое `isSubmitting`/pending-состояние.
- Если серверная ошибка однозначно относится к полю, преобразуйте её в field error и свяжите с контролом тем же ARIA-контрактом.
- Если ошибка относится ко всей операции, показывайте form-level сообщение; не помечайте произвольное поле невалидным.
- Не очищайте введённые значения после неуспешного submit.

## Render stability

- Значения, попадающие в dependencies validation effects, должны иметь стабильную identity при неизменных данных.
- Не создавайте новый объект или массив на каждом render, если изменение его ссылки повторно запускает валидацию или синхронизацию.
- Мемоизируйте derived value по фактическим inputs; не используйте `useMemo` без identity-контракта.
- Не связывайте effect по кругу: `effect → validate/setValue → render → новая dependency → effect`.
- Для пустых массивов и объектов в hooks используйте правила стабильных значений из [react.md](react.md#компоненты-react).

## Проверка и тестирование

Минимальная проверка формы с клиентской валидацией:

- первый invalid submit фокусирует первый актуальный невалидный контрол;
- повторный submit без исправлений фокусирует его же;
- после исправления первой ошибки следующий submit фокусирует следующую актуальную ошибку;
- `change` и `blur` не вызывают автоматический перенос фокуса;
- hidden container раскрывается до focus;
- disabled и нефокусируемые targets пропускаются;
- составные контролы корректно связаны со своими сообщениями;
- повторный submit отменяет устаревший запланированный focus;
- submit не создаёт render/validation loop;
- async-сценарии проверены по [правилам ожидания](#блокировка-действий-на-время-проверок) и [доступности действий](accessibility.md#асинхронная-проверка-и-disabled-действия);
- pure validators и нетривиальные переходы покрыты тестами согласно [testing.md](testing.md).

## Checklist для ревью

- Общие controls объединяют совпадающее поведение, а не только похожую разметку; различия API находятся в adapters.
- DI-контракты минимальны, сами хуки не передаются как зависимости; нет режимов и слоёв только ради будущего переиспользования.
- Submit проходит через form API и имеет один orchestration path.
- Required-ошибки не показываются преждевременно без продуктовой причины.
- Invalid submit всегда ведёт к первой актуальной ошибке, без cursor.
- Форма не перехватывает фокус при обычном вводе.
- Все видимые ошибки связаны со своими контролами.
- Связанная с автофокусом ошибка не объявляется повторно через `role="alert"`.
- Tabs/accordions раскрываются до попытки фокуса.
- Async submit защищён от дублирования и не теряет значения при ошибке.
- Состояния действий соответствуют [правилам ожидания](#блокировка-действий-на-время-проверок).
- Validation effects используют стабильные dependencies и не образуют цикл.
- Поведение проверено по [verification matrix](verification.md#verification-matrix): тестами на применимом seam и в браузере, если изменён пользовательский сценарий.
