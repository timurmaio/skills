# Delivery workflow

[Карта инженерной документации](../../CODING_STANDARDS.md).

Граница между локальной агентской работой и git-хостингом (GitLab, GitHub). Агент готовит проверенное изменение и материалы для handoff; пользователь управляет внешней публикацией.

## Authority

Локальный `git commit` — часть работы агента. Отдельное разрешение на каждый коммит не нужно: коммить готовый slice, когда обязательные checks прошли. Как резать slice и писать сообщение — skill `commit-changes` или commit-шаг специализированного skill.

Границы самостоятельного commit (когда пользователь сам запускает `commit-changes` или просит закоммитить, коммитится весь worktree в любой branch):

- **Только свои изменения.** Агент коммитит изменения текущей задачи. Pre-existing dirty/staged правки, не относящиеся к задаче, остаются нетронутыми и перечисляются в отчёте.
- **`{{MAIN_BRANCH}}` — только документация.** Без явного запроса в `{{MAIN_BRANCH}}` допустимы commits только из Markdown-документации и agent instructions, которые не попадают в сборку: `docs/**`, `AGENTS.md`, `CODING_STANDARDS.md`, `GLOSSARY-MAP.md`, `.agents/skills/**`, `src/features/*/docs/**`. Если slice содержит код, конфиг, зависимости или тесты, агент не коммитит его в `{{MAIN_BRANCH}}`: останавливается и предлагает создать ветку.
- **Рабочая ветка задачи** — любые commits в рамках задачи. Агент коммитит в неё и не переключается ради commit на `{{MAIN_BRANCH}}`.

Без отдельного явного запроса агент не выполняет:

- создание или переключение branch;
- `git push`;
- авторизацию на git-хостинге;
- создание или изменение MR/PR;
- публикацию комментариев и ответов;
- merge и release.

Push в защищённые ветки и перезапись удалённой истории запрещены и по явной просьбе: защищённые ветки меняются через MR/PR, хук `scripts/hooks/guardGitPush.mts` отказывает в таком push.

По умолчанию пользователь выполняет эти действия вручную. Setup не требует `glab`/`gh`, плагинов хостинга, API token или browser-автоматизации хостинга.

Инструкции upstream skills, включая сохранение prototype в throwaway branch, эти внешние действия не расширяют: skill готовит capture/staging plan и останавливается перед branch, push, MR/PR, merge и release.

## Локальный commit при failed check

Локальный commit не означает готовность изменения к MR/PR. Если обязательный общий check падает, commit допустим только при одновременном выполнении условий:

- доказано, что failure не связан с intended diff;
- применимые targeted checks для intended diff прошли;
- в отчёте указаны failed command, root cause и неподтверждённая часть.

Если независимость failure не доказана, агент останавливается до commit. Нельзя скрывать ошибку, отключать check или обходить commit hook. Даже после локального commit verification остаётся `NOT READY`, пока обязательный check не пройдёт; пользователь отдельно решает, публиковать ли такой snapshot.

## MR handoff

Перед ручным созданием MR/PR используйте `summarize-changes` в режиме MR handoff. Описание содержит:

1. Зачем: ticket и цель.
2. Что сделано: при необходимости схема изменения (дерево компонентов, вызовов или файлов, псевдокод, mermaid).
3. Опасность мержа: насколько просто откатить, что задето, что не проверено.
4. Как проверено: то, чего нет в CI, — браузер и до/после для бага и UI по свежему `verify-change` evidence.
5. Acceptance criteria с подтверждённым статусом.

Browser verification и screenshots решают разные задачи: browser доказывает поведение, screenshots помогают человеку быстрее проверить внешний вид. Для logic/API/refactor/docs/config screenshots не нужны.

## CI failure loop

1. Пользователь передаёт агенту failing command и первую actionable ошибку из CI.
2. Агент разбирает failure по `systematic-debugging`:
   - берёт первую actionable ошибку и её команду, повторы и шум лога пропускает; лог обрезан — просит первую ошибку;
   - воспроизводит её узкой командой: один test file, `pnpm --filter <package>`, один typecheck, а не весь `pnpm check`;
   - по пути определяет владельца — приложение, workspace package, config, generated, CI — и открывает его документ: `CODING_STANDARDS.md`, README пакета, документацию фреймворка из `node_modules`;
   - чинит причину, а не подавляет ошибку: без `eslint-disable`, `@ts-expect-error` и пропуска тестов; зависимости в корень не добавляет без причины.
3. После fix выполняются narrow check, полный `verify-change` и `review-changes` для затронутого scope.
4. Агент готовит краткий отчёт: root cause, fix, verification и текст ответа при необходимости.
5. Пользователь вручную делает push и обновляет MR/PR.

Агент не утверждает, что удалённый pipeline green, без свежего состояния или лога от пользователя.

## Review comments loop

1. Пользователь передаёт review comment вместе с контекстом файла или diff.
2. Агент проверяет замечание и отделяет actionable defect от вопроса, предпочтения или неверного предположения.
3. Для actionable finding агент делает минимальный fix; для остальных готовит доказательный ответ.
4. После изменения выполняются `verify-change` и `review-changes`.
5. Агент готовит текст ответа, пользователь публикует его и push вручную.

Loop завершён, когда предоставленные CI failures исправлены, actionable comments обработаны, локальный evidence свежий, а пользователь подтвердил актуальное внешнее состояние MR/PR.
