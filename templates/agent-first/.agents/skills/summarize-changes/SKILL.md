# Summarize Changes

Пиши для человека на языке пользователя; по умолчанию в репозитории — на русском. Не публикуй изменения и не взаимодействуй с git-хостингом.

## Scope

Собери факты через `git status --short`, релевантный `git log`, `git diff --stat` и focused diffs. Используй ticket/spec, `verify-change report` и `review-changes report`, если они доступны. Не выдумывай отсутствующее evidence. Утверждение из ticket или spec о коде («уже не вызывался», «поведение не меняется») сверь с diff и `git grep` до того, как писать.

## Режим summary

Используй по умолчанию для краткого описания изменений.

1. Выбери user-visible behavior, API, migrations, legacy removal, важные tests/docs/tooling.
2. Схлопни implementation details в один пункт; исключи formatting, file counts и metadata.
3. Верни 4–7 bullets или меньше для небольшого diff. Не добавляй heading, paths, hashes и branch names без запроса.

```markdown
- мигрировал PickerTree на react-aria-components Tree;
- удалил legacy Tree;
- вынес фокус/скролл в хук; добавил unit-тесты на pure-логику.
```

## Режим MR handoff

Используй, когда пользователь просит описание MR, handoff или полный отчёт для ручной публикации. Читатель — человек, который ревьюит MR/PR: ему нужно быстро понять, что и зачем, насколько внимательно смотреть и что доказывает работу.

```markdown
## Зачем

{{TICKET_KEY}}-1234 — <одна фраза о проблеме или цели>

## Что сделано

<схема — если без неё форму изменения не понять>

- <3–7 изменений поведения>

## Опасность мержа

**Откат:** простой | сложный — <почему: миграция, рассылка, удаление данных, изменение публичного API>
**Что задето:** <раздел или потребители, например «общая форма create и edit»>
**Не проверено:** <ограничения | —>

## Как проверено

- Браузер: <сценарий> — ✅/❌/не применимо
- До / после: <для бага или UI — как было и как стало, скриншоты>

## Критерии приёмки

- [x] <подтверждённый критерий>
- [ ] <неподтверждённый критерий — только если есть>
```

Правила:

- **Зачем.** Номер ticket бери из `bash ./.agents/skills/commit-changes/scripts/current-ticket.sh`; нет номера — только фраза о цели.
- **Схема** — необязательна: самый маленький вид, который показывает форму изменения, рядом с пунктом, который она поясняет. Выбери один, реже два:
  - дерево компонентов или вызовов с `+`/`-` в блоке `diff` — что добавилось и куда;
  - дерево файлов в блоке `diff` — для переезда и раскладки;
  - псевдокод в блоке `text` — для правила или алгоритма, до и после;
  - `mermaid` — для потока данных между частями.

  Строй её по diff, а не по ticket, и оставляй только имена, без которых не понять. Для docs, config и фикса в несколько строк схема не нужна.
- **Термины** — из `GLOSSARY.md` домена (`src/features/<domain>/docs/GLOSSARY.md`).
- **Откат сложный**, когда изменение нельзя просто откатить revert: миграция или удаление данных, отправленные пользователям сообщения, изменение API, от которого зависят другие. Остальное — простой.
- **Что задето** — по diff и потребителям изменённого кода: какие разделы и версии увидят изменение. Факт безопасности из `review-changes`, если есть, впиши сюда.
- **Не проверено** пиши и при успешных checks; не маскируй ограничения формулировкой «всё проверено».
- **Как проверено** — только то, чего CI не показывает: браузер, до/после, ручные сценарии. Результаты `pnpm check` и тестов не переписывай — их видно в pipeline; назови только проверку, которую локально пропустил или которая упала. Источник — свежий `verify-change report`; иначе явно напиши, что evidence отсутствует или устарел. Сверх CI показать нечего — раздел убери.
- **До / после** — для бага и заметного UI: 1–3 сфокусированных состояния. Для бага без UI — тест, который падал до фикса и проходит после: его название и что он проверяет одной строкой. Для logic, API, refactor, docs и config не нужно.
- Не отмечай критерий выполненным без diff или evidence. Нет критериев — раздел убери.
