# Capture Idea

Запиши заметку в [папку идей](../../../docs/ideas/README.md) после короткого обсуждения и закоммить её одним локальным коммитом в текущей ветке, когда пользователь одобрил черновик. Формат, статусы и правила совпадения живут в README. Сообщение коммита — по [Conventional Commits](../commit-changes/CONVENTIONAL_COMMITS.md).

Заметка без обсуждения превращается в мусор, а полный [grilling](../grilling/SKILL.md) при записи слишком долгий. Поэтому здесь один короткий стандартный проход: опись для себя, проверка идеи по разделу README «Проверка идеи», вердикт или до трёх вопросов, черновик после ответа, правки, сверка с описью, коммит после «да». Хочется копать глубже — это grilling, когда заметку берут в работу.

Пиши в заметку то, что прозвучало в разговоре, и факты, которые видны в коде. Смотри код столько, сколько нужно для четырёх целей:

- понять, о чём говорит пользователь: где живут фичи и места, которые он называет;
- проверить его утверждения и задать критические вопросы по существу;
- понять масштаб проблемы: где ещё она встречается и что входит в `Scope`;
- прикинуть грубый масштаб работы, чтобы сказать, сходится ли оценка пользователя.

Когда цели достигнуты, остановись. Решение не проектируй и точную оценку не выводи: нужен порядок величины, а не план. Свою оценку назови пользователю, но в `**Estimate:**` пиши только число пользователя. Секреты и токены в заметку не пиши.

Формат `**Estimate:**`, вопрос про оценку и то, когда дополнение её меняет, — по README. Если ответ не укладывается в формат, переспроси число.

Если по разделу README «Куда что идёт» запись сюда не относится, ничего не записывай и скажи, куда её направить.

Если вместе с идеей просят сделать изменение сейчас, выполни его как текущую задачу, а заметку запиши отдельно. Одобрение черновика разрешает один локальный коммит заметок этого прохода. Ветку не переключай. Push — отдельный явный запрос.

Если `docs/ideas/README.md` нет, остановись и скажи об этом. Папку и README не создавай.

## Workflow

1. **Прочитай заметки** — сначала `docs/ideas/README.md`, потом каждую заметку в `docs/ideas/`. README заметкой не считается. Запомни вывод `git status --short --untracked-files=all -- docs/ideas/`: это снимок до записи.
   **Done when:** README и все заметки прочитаны; у каждой заметки известны название, статус и суть; снимок запомнен.

2. **Составь опись** — нумерованный список всего, что установлено в разговоре и относится к запросу. Источник — весь разговор, а не последнее сообщение: проблемы, примеры, причины, последствия, решения, сомнения, ответы пользователя и твои находки в коде, включая те, что спорят с пользователем. Один пункт — один факт, пример, причина, решение или отвергнутая альтернатива с её причиной; сливай только пункты с одним и тем же содержанием. Идея из одного сообщения даёт опись из её пунктов. Затем раздели опись на отдельные работы по правилам README и для каждой выбери: дописать существующую заметку или создать новую. Опись — твой рабочий инструмент: по ней шаг 6 сверяет записанное. Пользователь видит из неё только список «Не вошло» в черновике.
   **Done when:** каждое утверждение разговора по теме запроса стоит в описи отдельным пунктом, включая то, что пользователь вынес за рамки запроса; на каждую работу приходится одна заметка.

3. **Проверь идею и скажи вердикт** — посмотри код по целям выше и поставь каждому пункту описи один вердикт: `в заметку`, `отброшено — причина` или `уже записано — где`. Вынесенное пользователем за рамки запроса — `отброшено — вне запроса`. Прогони идею через «Проверку идеи» в README: на каждый из четырёх вопросов нужен факт — файл, коммит, случай или место в разговоре. Факт не из кода (веб-поиск, чужой отчёт) помечай источником и «не перепроверено». Идею из твоего же разбора в этом разговоре назови своей и проверь как чужую. Затем ответь по итогу проверки. В ответ идёт только то, что нужно пользователю для решения; остальные находки пригодятся в черновике или когда он спросит.
   - **Идея слабая** — проблемы нет или она уже решена, работа не окупится, или тот же результат даёт путь заметно дешевле. Скажи это прямо: вердикт одной фразой и до трёх причин, по строке с фактом на каждую. Есть путь дешевле — назови его одной строкой. Идея пришла из внешнего источника и пользователь просил объяснить её — начни с сути в одном-двух предложениях. Закончи вопросом, записывать ли всё равно. Это всё сообщение: черновик появится, только если пользователь решит записывать.
   - **Уже записано** — каждый пункт описи уже лежит в открытой заметке. Дай ссылку на неё и спроси, что нового пользователь хочет добавить.
   - **Слабая только часть** — одной строкой назови отброшенную часть и причину, дальше как для живой идеи.
   - **Идея живая** — одной-двумя строками скажи, почему стоит записать, и задай до трёх вопросов. Сначала — критические, по пунктам проверки, которые вызвали сомнение. Потом — о том, чего не хватает для `Problem`, `Value` или estimate. Число уже прозвучало — скажи, сходится ли оно с масштабом в коде. Сомнений нет и всё прозвучало — вопросов нет, переходи к шагу 4 в этом же ответе.

   Файл не пиши и остановись до ответа.
   **Done when:** у каждого пункта описи один вердикт; пользователь увидел вердикт с причинами и вопросом, записывать ли всё равно, ссылку на заметку, где идея уже записана, или вопросы по живой идее, и ответа ещё нет. Либо вопросов нет и ты перешёл к шагу 4.

4. **Покажи черновик** — по ответу на шаг 3. Пользователь решил не записывать — ничего не пиши, проход окончен. Иначе заполни шаблон README по описи и ответам: пункт с вердиктом `в заметку` переносится вместе со своим примером, причиной и последствием. В `**Estimate:**` — число пользователя; числа ещё нет — оставь плейсхолдер и спроси его в этом же сообщении. Дату оставь плейсхолдером. Пользователь настоял на записи после вердикта «слабая» — твои причины идут в `Concerns`. Проверка, на которую не нашлось факта, тоже идёт в `Concerns` как «примера нет». Покажи одним сообщением:
   - текст новой заметки целиком. Для дополнения — только изменённые разделы и два списка: что убрано и что переформулировано со сменой смысла. Списки не пиши по памяти: сравни черновик с текущим файлом и найди каждое имя в обратных кавычках и каждое предложение прежнего текста, которых дословно нет в черновике. Каждую находку отнеси к одному из трёх: перенесено без смены смысла, переформулировано, убрано. Показывай два последних, с прежней и новой формулировкой;
   - «Не вошло»: пункты описи с вердиктами `отброшено — причина` и `уже записано — где`, по строке на пункт. Пункты `в заметку` видны в черновике, а `вне запроса` пользователь вынес сам, поэтому в список они не входят;
   - вопрос, записывать ли так.

   Остановись до ответа.
   **Done when:** каждый пункт `в заметку` находится в тексте черновика; пользователь увидел черновик, список «Не вошло» и вопрос, а ответа ещё нет.

5. **Запиши заметки** — после ответа внеси правки и запиши файлы строго по README. Новый раунд вопросов не начинай: если ответ меняет суть, покажи исправленный черновик ещё раз и снова дождись «да». При повторном показе:
   - пункт уходит из черновика только со сменой вердикта на `отброшено — причина`; назови каждый такой пункт;
   - если ответ перекрывает твоё возражение по scope или оценке, один раз скажи прямо: что решил пользователь, с чем ты не согласен и чего это стоит. Пользователь остался при своём — запиши несогласованный остаток в `Concerns` вместе со своим числом. Договорились — в заметку возражение не идёт.

   Дополнение записывай по правилам README. Записывай только тот текст, для которого пользователь видел списки убранного и переформулированного. После записи повтори сравнение по `git diff` файла: если в нём есть удаление, которого не было в показанных списках, назови его и дождись «да» до коммита. Дату возьми из `date +%F`.
   **Done when:** пользователь одобрил последний показанный текст. В дополнении затронутые разделы переписаны, в `Context` лежит строка `- YYYY-MM-DD: …`, и каждое удаление из `git diff` есть в списках, которые видел пользователь. В новой заметке есть `**Status:**`, `**Estimate:**` одним числом, `Problem` и `Value`, пустых разделов нет; в конце списка «Записи» есть строка `- [название](file.md) — одна строка сути`, строки «Пока записей нет.» нет.

6. **Сверь с описью** — перечитай каждую записанную заметку из файла целиком. Для каждого пункта описи с вердиктом `в заметку` найди раздел, где он лежит. Пункт не нашёлся — допиши его до коммита.
   **Done when:** у каждого пункта `в заметку` назван раздел файла, где он записан; дописанное на этом шаге перечислено.

7. **Собери пути** — из корня репозитория. Заметка входит в коммит, только если её пути не было в снимке шага 1. README входит, только если в этом проходе ты его менял и его не было в снимке. Дальше `git add --` только эти пути: без `-A` и без `.`. Если путей нет, коммит не делай.
   **Done when:** пути перечислены и добавлены в индекс. Файл из снимка в них не входит, и ответ говорит, что его правка осталась только на диске.

8. **Закоммить** — из корня репозитория запусти `bash ./.agents/skills/commit-changes/scripts/current-ticket.sh`. Если скрипт вернул номер, добавь его в сообщение. Если скрипт упал или ничего не вернул, номера нет: не придумывай. Текст: `docs(ideas): зафиксировать <краткая суть>` или `docs(ideas): {{TICKET_KEY}}-123 зафиксировать <краткая суть>`. Коммит: `git commit -m "<текст>" -- <пути>`: pathspec оставляет чужие staged-правки вне коммита. Без `--no-verify`. Если hook упал, не обходи его. После коммита проверь `git show --name-only --format='%h %s' HEAD`.
   **Done when:** в ответе есть пути и hash коммита, и `git show` содержит ровно эти пути. Либо причина, почему commit не прошёл и заметки остались на диске. В ответе есть итог: какие файлы записаны, что дописано при сверке и какие пункты ушли из черновика после его показа. Последняя строка — статус записи, не ответ на вопрос. `Запись закрыта.` — вне репозитория не осталось ни одного пункта `в заметку`. `Запись не закрыта: <что осталось>.` — иначе, с перечислением этих пунктов.
