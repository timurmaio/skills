# Фич-модули как deep modules

Фичу стоит проектировать как deep module: один явный фасад, строгие импорт-границы и полная инкапсуляция реализации внутри модуля.

## Что считается глубоким модулем

Фича — глубокий модуль, если выполнены все пункты.

- На карте системы имена совпадают с папками один к одному: `auth`, `wishlist`, `billing`, `search` — это `features/auth`, `features/wishlist` и так далее.
- У каждой важной фичи одна явная точка входа (`index.ts`). Через неё идёт всё взаимодействие снаружи.
- Логика, типы и хелперы инкапсулированы внутри фичи и не расползаются в абстрактный общий `lib/`.
- Тесты, сторибуки и контрактные тесты завязаны на публичный фасад, а не на внутренние файлы.
- Снаружи для работы с системой нужно держать в голове несколько крупных модулей и их интерфейсы, а не десятки мелких утилит.

## Фасад как слой отбора

`index.ts` — слой вкуса и отбора. Файл решает, что именно считается API фичи. Остальное остаётся внутренней деталью.

Явный экспорт можно переименовать на границе, чтобы контракт читался без знания внутренней структуры:

```ts
export { LoginForm as AuthLoginForm } from "./ui/login-form";
```

Barrel вида `export *` создаёт точку входа только формально:

- наружу вываливается набор случайных сущностей;
- эволюция затрудняется, потому что всё становится случайно публичным;
- контракт размывается, и непонятно, что действительно можно использовать.

Правильный barrel — только явные экспорты нужных компонентов, хуков и типов.

## Один официальный путь

Чтобы и люди, и агент реально пользовались интерфейсом, границу нужно заэнфорсить, а не только описать.

- В `tsconfig` `paths` алиас есть на корень фичи (`@/features/auth`) и отсутствует на внутренние папки (`@/features/auth/ui`, `@/features/auth/model`).
- ESLint (или своё правило) запрещает `import` из внутренних путей и разрешает только фасад:

```ts
import { Something } from "@/features/some-feature";
```

Официальный путь ровно один. Внутренние относительные импорты остаются внутри папки фичи и не становятся вторым API.
